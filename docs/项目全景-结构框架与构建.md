## 0. 一句话定位与规模

自研隧道协议的跨平台 VPN 教学项目：**12 字节报文头 + 三阶段身份认证 + AES-256-GCM 数据面**；
Windows/Linux 客户端共用一套 Qt GUI + 纯 C++ 业务核，Linux 服务端做多会话转发，
Android 是零 native 依赖的 Kotlin 重写，外层再套一套 Ed25519 验签驱动的更新 / 授权体系。

| 部分 | 语言 | 规模 | 备注 |

| 客户端 `src/` + `Config.*` + `Crypt.*` | C++17/20 | ≈ 16.7k 行 | 不含 `moc_*` / `ui_*` 生成物 |

## 3. 协议层（两端 + Android 三方必须逐字节一致）

### 3.1 帧头

`src/tunnel_protoco.h:5-14`（服务端 `server/Buffer/tunnel_protoco.h` 必须同线）：

```cpp
#pragma pack(push,1)
struct tunnel_header {
    uint32_t magic;        // 0x4D56504E ("MVPN")
    uint8_t  version;      // 1=v_udp / 2=v_tcp —— 同时是传输标识
    uint8_t  type;         // 消息类型
    uint16_t payload_len;  // 网络序
    uint32_t sequence;     // 网络序
};                          // 12 字节
```

字节序是**混合**的：magic 按主机序（Android 侧按小端字节 `4E 50 56 4D` 直接比对，
见 `android/.../tunnel/Protocol.kt:15`），`payload_len` / `sequence` 走大端。
版本字节即传输标识 —— 发错传输的报文在接收侧 version 校验处自然被丢弃。

### 3.2 消息类型

| 值 | 名称 | 方向 | 明文/密文 |
|---|---|---|---|
| 0/1 | `m_hand_request` / `m_hand_response` | C↔S | 明文（旧握手残留） |
| 2 | `m_data` | 双向 | 密文 |
| 3/4 | `m_heart` / `m_heart_response` | 双向 | 密文 |
| 5 | `disconnect` | 双向 | 密文 |
| 6/7 | `m_key_exchange` / `m_key_response` | C↔S | 明文（旧流程残留） |
| 8 | `m_auth_hello` | C→S | 明文 `nonce_c(16)` |
| 9 | `m_auth_server_hello` | S→C | 明文 `nonce_s(16)‖dh_srv_pub(32)‖sig(64)` = 112 |
| 10 | `m_auth_client_hello` | C→S | 明文 `dh_cli_pub(32)` |
| 11 | `m_identity` | C→S | 密文内层 |
| 12 | `m_identity_ok` | S→C | 密文内层 `vip(4)‖prefix(1)` |
| 13 | `m_identity_deny` | S→C | 密文内层 `reason(1)`：0=未注册/验签失败，1=令牌无效/已用 |

### 3.3 三阶段认证

```
客户端                                          服务端
  │ ① auth_hello[nonce_c] ──────────────────────►│ 建 Session(pending)
  │◄──────────── auth_server_hello[nonce_s‖dh_srv_pub‖sig_srv] │
  │   用内置 SIG_SRV_PUB 验签；sig 覆盖 nonce_c‖nonce_s‖dh_srv_pub │
  │   验签失败 = 中间人 → 直接断开（不降级、不重试）              │
  │ ② auth_client_hello[dh_cli_pub] ─────────────►│
  │   ss    = X25519(dh_cli_priv, dh_srv_pub)     │ 同左
  │   prk   = HKDF-Extract(salt = nonce_c‖nonce_s, IKM = ss)
  │   key_tx= Expand(prk,"tx",32)                 │ key_c2s
  │   key_rx= Expand(prk,"rx",32)                 │ key_s2c
  │ ③ identity(密文)：会话上下文‖client_id‖SIG_CLI_PUB‖token‖签名 ►│ 验签 + 查注册库
  │◄──────────────────── identity_ok(密文) / identity_deny(密文) │
  │                                                              │
  │ ═══════════ 认证通过前服务端不转发任何流量 ═══════════════════ │
```

实现位置：
- 客户端状态机：`src/UDP.cpp:534` `send_work()`（发送侧重传）、`src/UDP.cpp:805` `handle_frame()`（接收侧推进）
- 服务端状态机：`server/UDP/UDP.cpp:1281` `handle_auth_hello`、`:1381` `handle_auth_client_hello`、`:1452` `handle_identity`

### 3.4 数据面封装

```
m_data payload = inner_type(1) ‖ nonce(12) ‖ ciphertext(N) ‖ tag(16)
约束：N ≤ 1400（KMax_data_payload），总计 ≤ 1429（Max_payload_len）
AAD 覆盖帧头 → sequence 不可篡改
```

`1400 + 1 + 12 + 16 = 1429`，对应 TUN MTU 1400，两端常量在各自 `tunnel_protoco.h` 里对齐。

### 3.5 反重放与序号

- **滑动窗口** 64 位位图，`server/UDP/Session.h:35`（客户端 `src/replay_window.h` 同款）
- 顺序铁律：`too_old()` 预检（**不修改状态**）→ AES-GCM 验证成功 → `accept()` 提交。
  先提交会把伪造高序号写进窗口，后续合法报文被误判"太旧"
- **序号上限** `kSeqRekeyLimit = 0x80000000`（2^31）：达到即强制重连换新密钥，
  防 32 位回绕被滑窗误判

## 4. 客户端框架

### 4.1 ClientApp 生命周期

`src/client/ClientApp.h:47`，三个公开入口：

| 方法 | 职责 |
|---|---|
| `init()` | config → 身份密钥（Windows DPAPI / Linux 0600）→ TUN → 适配器 → 路由；`is_elevated()` 检查 |
| `start()` | 启动 `ReconnectManager` + 两条桥接线程（`tun_to_udp_loop` / `udp_to_tun_loop`），立即返回 |
| `stop()` | 停隧道 → 清路由 → 恢复 DNS → join，可重复调用 |

**四道闸门**（都在 `ClientApp` 里，防止绕过 UI）：

| 闸门 | 作用 |
|---|---|
| `m_updateBlocked` | 强制更新未完成时禁止连接（防托盘/命令行绕过） |
| `m_serviceBlocked` | 受管服务判定不允许使用时禁止连接 |
| `m_tunIpReady` | 服务端通告的虚拟 IP 还没落到网卡前，禁止上行（否则源地址防伪整片丢包） |

### 4.2 UDP 基类 = 模板方法模式

`src/UDP.h:25`。基类实现全部协议逻辑，子类只覆写 **4 个钩子 + 1 个版本字节**：

```cpp
virtual sock_t open_socket();                              // UDP: SOCK_DGRAM / TCP: SOCK_STREAM
virtual bool   establish();                                // UDP: no-op / TCP: connect + NODELAY
virtual bool   raw_send(const uint8_t*, size_t);           // UDP: sendto / TCP: send_all
virtual bool   recv_frame(hdr, payload, len, got);         // UDP: 一报一条 / TCP: 分帧状态机
virtual uint8_t proto_version() const;                     // 1 / 2
```

线程模型：`send_thread`（消费 `m_sendqueue`）+ `recv_thread`（`recv_frame` → `handle_frame`）。
`m_send_mutex` 串行化 socket 写 —— 两个线程都可能发送，TCP 流式写必须整帧原子。

### 4.3 TCP 子类

`src/tcp.h:19`。非阻塞 `connect` + 4s 超时 + `TCP_NODELAY`；接收侧
`take_frame()` / `compact_rx()` 做分帧，**只在读空或消费超 64KB 时 memmove 一次**，
不是每帧 `vector::erase`。

### 4.4 ReconnectManager

`src/reconnect_manager.h:26`。`ConnState` 五态（Stopped/Connecting/Connected/Reconnecting/Error）。
**每次连接新建 UDP 实例**（旧实例 stop 后队列不可复用），泵线程通过 `udp()` 每次取当前实例。
指数退避 + 握手等待 12s。

### 4.9 受管服务

```

                 ↑ v2 规则：CPU/RAM/MAC/OS 只做展示，不参与（v1 混入导致同一台机器漂移）
                 ↑ 读失败返回空，绝不退化为固定常量（否则所有机器共用假身份）
service_client   parse_credentials / evaluate / verify_signature（纯逻辑）
                 + register_trial / fetch_status / fetch_server_list（网络）
AppBridge        set_service_mode / check_service / register_service / apply_server_list
```

`evaluate()` 的闸门：`rejected` / 试用到期 / 配额耗尽 → `blocked`。
查不到（网络失败）→ **放行**（不能因为服务端挂了就锁死用户）。

## 5. 服务端框架

### 5.1 VpnCore

`server/core/VpnCore.h:21`。`init()` 建 TUN → 配地址/MTU/up → `udp.start()`；
`start()` 启两条转发线程（`forward_tun_to_udp` / `forward_udp_to_tun`）；
`stop()` 逆序清理。`TCPServer m_tcp{m_udp}` 组合引用同一份会话表。

### 5.2 UDP 多会话核心

`server/UDP/UDP.h:24`，实现 1919 行，是服务端最重的文件。三条线程：

| 线程 | 职责 |
|---|---|
| `send_work()` | TUN 下行包 → 查 VIP → 加密 → socket / TCP 队列 |
| `recv_work()` | 收包 → 分帧 → `handle_framed()` → 会话分发 |
| `heartbeat_work()` | 10s 心跳 / 30s 判死 / 配额与审计 flush |

会话键 `"ip:port/tcp|udp"`（**含传输协议**，TCP/UDP 不混用）。
`handle_framed()`（`:1062`）是 TCP 与 UDP 共用的唯一消息入口。

**握手重算限速**：`allow_handshake_recompute()`（`:417`）按来源 IP 令牌桶，
只对"带新 nonce 的 auth_hello"扣令牌 —— 这类请求要生成临时 X25519 密钥对 + Ed25519 签名，
不限制就是免费的 CPU 放大器。同 nonce 重传走幂等分支（查表 + 重发缓存）。

### 5.3 Session

`server/UDP/Session.h:122`。一个客户端连接的全部状态：认证阶段、密钥、发送队列、
TCP 跨线程发送队列（`tcp_tx` + 2MB 积压上限）、反重放窗口、流量计数、受管服务快照。

关键并发约定：认证状态机只在**单线程**跑（UDP recv 线程 或 TCP epoll 线程），
单会话内天然串行；跨线程只通过原子标志和队列交互。

`released` 标志兜住一个真实窗口：会话已从表摘除但 TCP 连接还挂着几十毫秒，
期间到达的明文 `auth_hello` 能让僵尸会话重新握手再领一个 VIP（池泄漏）。

### 5.4 TCPServer

`server/TCP/tcpserver.h:27`。单线程 epoll 管监听 + 全部连接，fd 全部非阻塞。
**本线程是连接 fd 的唯一 owner**，其他线程只置 `Session.tcp_drop`，由事件循环统一
`shutdown+close` —— 杜绝跨线程 close 的 fd 复用竞争。`eventfd` 做跨线程唤醒。

### 5.5 虚拟 IP 三级分配（踩过大坑的地方）

`VirtualIpPool`（`Session.h:241`）：

1. **租约**：`vip_leases.txt` 里 ClientID → 上次地址（持久化，重启不丢）
2. **身份派生**：`preferred_for(key)` 用 FNV-1a 哈希确定性映射（不用 `std::hash`，
   否则换编译器所有人地址全变）
3. **随机兜底**：`allocate()` 仅在候选被占时使用

历史教训写在 `Session.h:274-278`：曾经直接用随机分配，同一客户端每次重连换地址
→ 客户端必须改网卡 → 改地址窗口内上行包源地址还是旧的 → 被源地址防伪整片丢弃
→ 网速降到几十 K、隧道内 TCP SYN 都发不出去。**虚拟 IP 必须按身份稳定。**

### 5.6 ServiceDB（受管服务，可选）

`server/ServiceDB.h:39`。SQLite 访问层，`SVC_DB` 未配置或打不开时**全部能力自动停用**，
普通部署零影响。职责：

- 登录校验：读 `trials` 的 status/expire/quota（不在表里 = 手工注册老用户，不受约束）
- 流量：内存聚合 → `flush()` 批量写回 `used_bytes`
- 审计：`extract_domain()` 从隧道内 IPv4 包提取 DNS QNAME 或 TLS SNI（`:37`）
- 黑名单：domain（后缀匹配）/ ip（精确）/ machine（client_id），60s 重读

审计是**尽力而为**：分片、短包、QUIC、ESNI 一律静默跳过，绝不能拖慢转发路径。

### 5.7 后台四件套

| 可执行 | 源码 | 说明 |
|---|---|---|
| `admin_server` | `ServerAdmin/AdminServer.cpp` | 本地管理 API。**不解析 argv，只认环境变量**：`ADMIN_BIND`/`ADMIN_PORT`/`KEYS_DIR`/`ADMIN_TOKEN` |
| `admin_cli` | `ServerAdmin/ServerAdminClinet.cpp`（文件名拼写如此） | 子命令 `info`/`list`/`gen`/`del`；令牌走 env 不进 shell history |
| `admin_agent` | `ServerAdmin/Agent.cpp` | 反连中转；启动打印 64hex 身份指纹（= 白名单登记值） |
| `vpn_controller` | `ServerAdmin/Controller.cpp` | 中转；`--add-agent` 登记后**必须重启**才生效（白名单只在 start() 读一次） |

配套脚本：`server/admin-vpn.sh`（VPN 端）/ `server/admin-relay.sh`（中转端），
都带 `doctor` 自检和首次运行自动构建。

## 8. 一致性约束（改代码前必须知道）

### 8.1 协议同线（最硬的红线）

| 客户端 | 服务端 | 后果 |
|---|---|---|
| `src/tunnel_protoco.h` | `server/Buffer/tunnel_protoco.h` | 常量不一致 → 帧长度校验失败，全丢 |
| `src/Crypt.cpp` | `server/Crypt/crypt.cpp` | 封装格式不一致 → 解密全失败 |
| Android `Protocol.kt` | 上面两个 | 同上 |

改任意一侧，另外两侧必须同步，并跑 `docs/ANDROID_PROTOCOL_SPEC.md` 的逐字节核对。

### 8.2 新增源文件必须登记三处

1. `VPN_.vcxproj` → `ClCompile` / `ClInclude`
2. `VPN_.vcxproj.filters`
3. `CMakeLists.txt`（Linux 客户端）或 `server/CMakeLists.txt`（服务端）

漏登记在 AI 直编 cl.exe 时能过，**MSBuild 链接时才爆 LNK2019**（2026-10-31 踩过）。

### 8.3 其它约定

| 约定 | 原因 |
|---|---|
| `config.ini` **禁止用 QSettings** | QSettings 写 UTF-8，`GetPrivateProfileStringW` 按 ANSI 解码 → "香港"→"棣橣离"。统一走 `scholini::Ini*` |
| GUI 头文件改了信号槽 → 重跑 moc | Windows 用的是提交进仓库的 `moc_*.cpp`，不自动生成 |
| 服务端公钥硬编码在 `src/client/ClientApp.cpp` 的 `kServerSigPubPem` | 不在 `main.cpp` |
| `server-list` 的 `pubkey` 必须来自 `server/keys/server_sig.pub` | 误填 broker 的 service key → 客户端验签失败卡"连接中"（2026-11-01 事故） |
| 敏感信息不进客户端 | 例外：受管接入点 `scholarvpn.homes:8445` 随发行版内置（老板明确要求） |
| 项目路径含空格 `D:\Vis  c++\` | bash 会把 `/nologo` 当路径转换 → Windows 工具用 PowerShell 调 |

## 10. 通读发现的问题（按严重度）

> 以下是**静态阅读**的结论，未经运行验证；标注了判断依据。

### P1 — 会影响用户可见行为

**1. Linux 分发包缺 `chn-domains.txt` → DNS 分流静默失效**

- `CMakeLists.txt:83-85` 只 `install` 了 `chnroute.txt` 和 `style.qss`
- `scripts/build-linux.sh:66-72` 打包只 `cp docs/routing/chnroute.txt`
- 而 `DnsProxy` 需要 `chn-domains.txt`，加载失败就静默不启动 → 回落国内 DNS → 国外域名被污染

这和 AI_HANDOFF 里记录的 Windows 侧事故（"iss 打包补上 chn-domains.txt"）是同一类问题，
Windows 修了，**Linux 打包链没修**。验证方法：装完 `ls /opt/scholarvpn/` 看有没有该文件。

**2. `ScholarVPN.iss` 的 `[Files]` 缺 `style.qss` → 安装版没有样式表**

`ScholarVPN.iss:46-74` 列了 exe、Qt DLL、插件目录、分流数据、图标，**唯独没有 style.qss**。
`main.cpp:48-53` 从 exe 同目录读 QSS，读不到就静默跳过 → 安装版是 Qt 默认外观，
而 PostBuild 拷进 `x64/Release` 的那份只在开发机生效。

**3. 大量核心代码未提交（24 改 + 16 未跟踪）**

未跟踪里包含：`src/DnsProxy.{h,cpp}`、`server/ServiceDB.{h,cpp}`、
`docs/routing/chn-domains.txt`（109455 行）、`src/service/`、`tools/broker/`、
`docs/受管服务与试用授权方案.md`。

也就是说 **P3 DNS 分流 + 受管服务整条链路都还没进 git**。换台机器 clone 下来是残缺的。
另：`chn-domains.txt` 未入库 → 任何人 clone 后都无法构建出可用的分流包。

### P2 — 工程一致性问题

**4. `ScholarVPN.iss` 的中文注释是双重编码乱码**

文件是 UTF-8 with BOM，但内容是"UTF-8 字节被当 GBK 解码后又存成 UTF-8"的产物
（`客户端` → `瀹㈡埛绔`）。功能不受影响（注释而已），但没人能读懂，改脚本时容易误操作。

**5. Windows 用静态 CRT（/MT、/MTd），Qt6 官方是 /MD**

`VPN_.vcxproj:57 / :97`。跨 DLL 边界传 Qt 对象时理论上存在堆不匹配风险
（实际 UCRT 默认都走进程堆，通常能跑，但不保证；Debug 混用风险更高）。
另外 AI_HANDOFF 里手工 cl.exe 的参数写的是 `/MD`，与工程文件不一致 —— 两条路径产出的
二进制 CRT 模型不同，回归测试时别混用。

**6. `VPN_.vcxproj` 的 `ClInclude` 漏登记 `src/DnsProxy.h`**

`:128-163` 有 `DnsProxy.cpp`（`ClCompile`）但没有对应头文件条目。
不影响编译（头文件不参与构建），但违反项目自己的"三处登记"规矩，且 VS 解决方案里看不到它。

**7. 根目录 `ServerAdmin/` 是遗留 Qt 工程，仍在 git 里**

与 `server/ServerAdmin/` 同名不同物，且子目录名 `svever` 拼错。建议移到 `legacy/` 或删除。

### P3 — 整洁度

**8. 工作区根目录有构建垃圾**：`mini.i`(6.0MB) / `dnsmini.i`(3.7MB) / `DnsProxy.i`(6.4MB)
是预处理器输出；`crypt.obj` / `stub.obj` / `test.obj` / `test_win.obj` 是散落的 .obj。
`.gitignore` 已挡住，但占地方也容易误读。

**9. `docs/架构分析.md` 已过时**（2026-10-17，缺更新/受管/分流/Android/后台），
建议加一行指向本文，或直接归档。
