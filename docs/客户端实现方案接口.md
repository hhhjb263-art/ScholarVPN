## 0. 一页纸速览

```
┌──────────────┐   HTTP 18081（Bearer）   ┌────────────────┐   TCP 19090（握手+JSON帧）  ┌──────────────┐   HTTP 18080   ┌─────────────┐
│ 管理客户端    │ ───────────────────────▶ │ vpn_controller │ ◀────────────────────────── │ admin_agent  │ ─────────────▶ │ AdminServer │
│ Web/Qt/CLI   │ ◀─────────────────────── │   （中转站）    │ ──────────────────────────▶ │（VPN服务器侧）│ ◀───────────── │（业务执行层）│
└──────────────┘    JSON 响应              └────────────────┘   命令帧/回执帧              └──────────────┘   HTTP 响应     └─────────────┘
                                             公网/内网入口              各 agent 出站反连              本机环回
```

| 接口面 | 默认地址 | 传输 | 鉴权 | 谁连谁 |
|---|---|---|---|---|
| A. 管理 HTTP | `127.0.0.1:18081` | HTTP/1.1 明文，`Connection: close` | `Authorization: Bearer <controller 的管理令牌>` | 管理客户端 → controller |
| B. Agent 通道 | `0.0.0.0:19090` | 裸 TCP，4 字节大端长度 + JSON 帧 | Ed25519 挑战签名 + 公钥指纹白名单 | agent **出站** → controller |

两条铁律：

1. **帧 = `[4 字节大端长度][JSON 载荷]`**，单帧 ≤ 65536 字节（`AdminWire.h:24`）。
2. **每一帧都是扁平 JSON 对象**，值只能是字符串或整数——没有嵌套对象、没有数组、没有浮点、没有 `\u` 转义。
   业务 body 作为**字符串字段**传输，内部 JSON 自己再转义一层。

## 1. 组件与端口

| 组件 | 位置 | 默认端口 | 环境变量 | 说明 |
|---|---|---|---|---|
| `vpn_controller` | 中转服务器 | agent 通道 **19090**，HTTP 入口 **18081** | `AGENT_BIND`/`AGENT_PORT`/`HTTP_BIND`/`HTTP_PORT`/`ADMIN_TOKEN`/`AGENTS_FILE` | 本协议的服务端；**一期同时只服务一个 agent 连接**（见 6.8） |
| `admin_agent` | 每台 VPN 服务器 | 出站连 19090 | `CONTROLLER_HOST`/`CONTROLLER_PORT`/`ADMIN_HOST`/`ADMIN_PORT`/`KEY_PATH`/`ADMIN_TOKEN`/`AGENT_NAME` | 反连 controller，把命令转给本机 AdminServer |
| `admin_server` | 每台 VPN 服务器 | 18080（环回） | `ADMIN_BIND`/`ADMIN_PORT`/`KEYS_DIR`/`ADMIN_TOKEN` | 真正执行业务的 HTTP 服务（已完成） |
| 管理客户端 | 管理员电脑 / 浏览器 | — | — | 只跟 controller 的 18081 说话 |

部署约束（当前明文实现）：

- `19090` **必须**置于内网 / VPN / 防火墙白名单之后，绝不能裸奔在公网；
- `18081` 默认只绑环回，远程管理用 `ssh -L 18081:127.0.0.1:18081`；
- 管理客户端**不需要**能访问任何 VPN 服务器的 18080。

## 2. 接口面 A：管理 HTTP（controller:18081）

### 2.1 通用约定

| 项 | 值 |
|---|---|
| 协议 | HTTP/1.1，明文 |
| 连接 | 一个请求一条短连接，服务端回完即 `close`（响应带 `Connection: close`） |
| 请求上限 | 头 + body ≤ **8192 字节**，超出 413 |
| 响应 `Content-Type` | 恒为 `application/json`（包括转发的 `/info`） |
| 转发语义 | 路径中的 `{id}` 之后的部分**原样**变成 agent 侧 AdminServer 的路径；method/body 原样过隧道 |
| 路径编码 | controller **不做** URL percent-decode；`{id}` 不能含 `/`、空格、非 ASCII |

### 2.2 鉴权

```
Authorization: Bearer <ADMIN_TOKEN>
```

- 比较是常量时间（`CRYPTO_memcmp`，`Controller.cpp:393-402`）；
- `ADMIN_TOKEN` 为空时**完全不鉴权**（仅限本机调试；启动时建议永远设置）；
- 401 的 body 固定为 `{"error":"unauthorized"}`。

### 2.3 端点总表

| 方法 | 路径 | 转发到 agent 的 | 说明 |
|---|---|---|---|
| GET | `/api/servers` | —（controller 本地生成） | 当前在线 agent 列表 |
| GET | `/api/servers/{id}/info` | `GET /api/info` | 公钥 / IP / 端口 |
| GET | `/api/servers/{id}/tokens` | `GET /api/tokens` | 未消费令牌列表 |
| POST | `/api/servers/{id}/tokens` | `POST /api/tokens` | body `{"count":N}`，1..1000 |
| DELETE | `/api/servers/{id}/tokens/{token}` | `DELETE /api/tokens/{token}` | 删除未消费令牌 |

其余路径一律 `404 {"error":"not found"}`。注意：**没有** `GET /` 管理页，也没有 controller 自身的 `/api/info`。

### 2.4 GET /api/servers

响应（`Controller.cpp:501-518`）：

```json
{
  "servers": [
    {
      "id": "hk-01",
      "pubkey_hex": "25d87aa460a40de6ff62a2fac3dee2c8c1cf99dcc424d31c2be8863a5549b446",
      "ip": "203.0.113.7",
      "last_seen": 128374923
    }
  ]
}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | string | agent 的展示名；agent 未配 `--name` 时 = 公钥前 8 位 hex |
| `pubkey_hex` | string | 64 位小写 hex，agent 身份公钥（白名单指纹） |
| `ip` | string | agent 反连的来源 IP |
| `last_seen` | int | **controller 进程的单调时钟毫秒**（`steady_clock`），不是 Unix 时间戳 |

⚠️ `last_seen` 只能用于「同一份列表内比较新旧」或直接显示为“活动中”；**不要**当日期时间格式化。
二期会改成 Unix 毫秒或 ISO-8601。

列表里只有**当前在线**的 agent（断开即从表中移除），所以没有 `online` 字段。
一期 controller 的 agent 通道是单连接的，因此这个列表**最多只有 1 个元素**（见 6.8）。

### 2.5 四个转发端点

#### GET /api/servers/{id}/info

成功时原样返回 AdminServer 的 `/api/info` 响应（200）：

```json
{
  "version": "1.0",
  "pubkey_pem": "-----BEGIN PUBLIC KEY-----\n...\n-----END PUBLIC KEY-----\n\n",
  "pubkey_hex": "25d87aa4...",
  "ip": "0.0.0.0",
  "port": 51820
}
```

#### GET /api/servers/{id}/tokens

```json
{ "tokens": ["a1b2...64hex", "c3d4...64hex"] }
```

#### POST /api/servers/{id}/tokens

请求 body：

```json
{ "count": 5 }
```

成功响应：

```json
{ "tokens": ["新令牌1", "新令牌2", "..."] }
```

`count` 不合法时，agent 侧 AdminServer 返回 `400 {"error":"count must be 1-1000"}`，controller 原样透传。

#### DELETE /api/servers/{id}/tokens/{token}

成功：

```json
{ "deleted": true }
```

令牌不存在（可能已被注册消费）：

```json
{ "error": "token not found" }
```

HTTP 状态 404。

### 2.6 错误码与「谁产生的」区分

| HTTP | body | 产生方 | 含义 |
|---|---|---|---|
| 401 | `{"error":"unauthorized"}` | **controller** | 管理令牌缺失/错误 |
| 400 | `{"error":"bad request"}` | controller | 报文不完整/请求行坏 |
| 413 | `{"error":"request too large"}` | controller | 请求 > 8KB |
| 404 | `{"error":"not found"}` | controller | 路径不认识（含 `/api/servers/{id}/xxx` 未知子路径） |
| 503 | `{"error":"agent offline"}` | controller | 该 id 当前没有在线连接；**不排队**，直接失败 |
| 504 | `{"error":"agent timeout"}` | controller | 命令已发出，10 秒内没收到回执 |
| 504 | `{"error":"agent send failed"}` | controller | 命令帧写 socket 失败（连接已坏） |
| 200/400/401/404/405/500 | 各业务 JSON | **agent 侧 AdminServer** | 原样透传（如 `count` 越界、令牌不存在、本机令牌配错） |

⚠️ **401 的二义性**：controller 鉴权失败和 agent 侧 AdminServer 鉴权失败**都可能是 401 + `{"error":"unauthorized"}`**。
排查顺序：先确认 `ADMIN_TOKEN`（controller 的），再确认 agent 启动参数 `--token`（本机 AdminServer 的管理令牌）。
同理 `404 not found` 也可能来自两侧。

### 2.7 curl 示例

```bash
TOKEN=<controller 的 ADMIN_TOKEN>
BASE=http://127.0.0.1:18081

curl -H "Authorization: Bearer $TOKEN" $BASE/api/servers

curl -H "Authorization: Bearer $TOKEN" $BASE/api/servers/hk-01/info

curl -H "Authorization: Bearer $TOKEN" \
     -X POST -d '{"count":3}' $BASE/api/servers/hk-01/tokens

curl -H "Authorization: Bearer $TOKEN" \
     -X DELETE $BASE/api/servers/hk-01/tokens/<64hex>
```

## 3. 接口面 B：Agent 通道（controller:19090）

### 3.1 帧格式（逐字节）

```
偏移  长度  字段        编码
0     4    payload_len  大端 uint32（网络字节序），= 后续 JSON 的字节数
4     n    payload      UTF-8 JSON 文本（扁平对象）
```

- `payload_len` 上限 **65536**（`AdminWire.h:24`），超限接收方必须断开连接；
- `payload_len` 允许为 0 吗？代码里 `Framer::next` 会取出空串，随后 JSON 解析失败——
  实际上不会发生，发送方永远发至少 `{}`；
- 帧与帧之间**没有**分隔符、没有 magic、没有校验和、没有版本号；
- 两个方向的帧格式完全相同。

### 3.2 JSON 子集（最容易写错的地方）

`AdminWire.h` 的解析器**不是通用 JSON 解析器**，它只做扁平对象的字段查找：

| 允许 | 禁止 |
|---|---|
| 对象 `{ "k": "v", "n": 123 }` | 嵌套对象：`{"a":{"b":1}}` |
| 字符串值（含转义 `\" \\ \n \r \t \/`） | 数组：`{"tokens":[...]}` ← 注意！ |
| 整数值（`strtoll`） | 浮点、布尔、`null` |
| UTF-8 原文 | **`\uXXXX` 转义**（解析器会把它变成字面量 `u4e2d`） |

三条实操结论：

1. **令牌数组不能直接作为帧字段**。帧里只有 `body` 字符串，数组在 body 内部：
   `{"type":"reply","id":7,"status":200,"body":"{\"tokens\":[\"a1b2...\"]}"}`。
2. **中文不要用 `\u` 转义**。Python 写客户端时必须 `json.dumps(..., ensure_ascii=False)`，
   否则 `--name "香港-01"` 到 controller 会变成乱码；C++ 直接把 UTF-8 原样拼进去即可。
3. 发送方把 `body` 放入外层 JSON 时，只需转义 `"` `\` 和换行/制表符——controller 的
   `wire::escape()` 就是这么做的（`AdminWire.h:28-43`）。

### 3.3 握手状态机

```
agent                                   controller
  │                                          │
  │ ──────── TCP connect 19090 ────────────▶ │  accept（单线程，握手期间不接受新连接）
  │                                          │
  │ ◀── {"type":"challenge","nonce":"32hex"} │  16 字节 CSPRNG → 32 位小写 hex
  │                                          │
  │  用本机 Ed25519 私钥对 nonce 的          │
  │  **16 字节原始值**签名（不是 hex 字符串） │
  │                                          │
  │ ─── {"type":"hello",                     │
  │      "pubkey_hex":"64hex",               │  校验签名 + 白名单
  │      "sig":"128hex",                     │
  │      "name":"hk-01"} ──────────────────▶ │
  │                                          │
  │ ◀── {"type":"welcome","id":"hk-01"}      │  成功
  │   或 {"type":"reject","reason":"..."}    │  失败后立即 close
  │                                          │
  │ ══════ 长连接：心跳 + 命令/回执 ══════ │
```

关键约束：

- **controller 先发 challenge**，agent 连上后必须先等这一帧，不能主动发 hello；
- 握手每一步的超时都是 **5 秒**（`wire::kTimeoutMs`）；
- 签名的对象是 `nonce` **hex 解码后的 16 字节**（`Agent.cpp:196-208`），不是 32 字符 hex 文本；
- `pubkey_hex` 是 agent 私钥对应的 **32 字节公钥**的 64 位小写 hex；
- `sig` 是 64 字节签名的 128 位小写 hex；
- `name` 可省略或为空串；为空时 controller 用公钥前 8 位作 `id`。

### 3.4 帧类型总表

| type | 方向 | 字段 | 说明 |
|---|---|---|---|
| `challenge` | C → A | `nonce`: string(32hex) | 连接建立后的第一帧，一次性 |
| `hello` | A → C | `pubkey_hex`: string(64hex)<br>`sig`: string(128hex)<br>`name`: string(可空) | 准入请求 |
| `welcome` | C → A | `id`: string | 准入成功，`id` 是该 agent 的固定标识 |
| `reject` | C → A | `reason`: string | 准入失败，随后 controller 关闭连接 |
| `heartbeat` | A → C | 无 | 每 15 秒一次，controller **不回复** |
| `command` | C → A | `id`: int<br>`method`: string<br>`path`: string<br>`body`: string | 一次业务调用 |
| `reply` | A → C | `id`: int<br>`status`: int<br>`body`: string | 对应 command 的结果 |

方向：C = controller，A = agent。

字段类型：

- `id`（command/reply）：64 位有符号整数，controller 进程内从 1 自增。
- `status`：HTTP 状态码整数。
- `body`：字符串，内容为原始 JSON 文本（可能为空串）。

### 3.5 心跳与失联判定

| 项 | 值 | 位置 |
|---|---|---|
| 心跳周期（agent 发） | 15 s | `Agent.cpp:31` |
| 心跳帧 | `{"type":"heartbeat"}` | `Agent.cpp:338-344` |
| controller 失联判定 | **45 s**（3×15s）没收到该连接任何帧 | `Controller.cpp:33,323-327` |
| controller 对心跳的回复 | **无**（agent 不要等 pong） | `Controller.cpp:346` |

agent 侧没有应用层“等 pong 超时”：连接半开（拔网线）时只能依赖 TCP 自身超时或下一次
`send` 失败来发现。写第三方 agent 时若要快速发现半开，可自行加 `TCP_USER_TIMEOUT` 或
“45 秒没收到任何 controller 帧就主动断开”。

### 3.6 命令与回执

controller → agent：

```json
{"type":"command","id":7,"method":"POST","path":"/api/tokens","body":"{\"count\":5}"}
```

agent 执行：把 `method`/`path`/`body` **原样**作为 HTTP 请求发给本机 AdminServer
（`Connection: close`，带 agent 配置的 Bearer），拿到状态码与响应体。

agent → controller：

```json
{"type":"reply","id":7,"status":200,"body":"{\"tokens\":[\"a1b2...\",\"c3d4...\"]}"}
```

特殊情况：

- 本机 AdminServer 连不上 → agent 回 `{"type":"reply","id":7,"status":502,"body":"{\"error\":\"local admin server unreachable\"}"}`（`Agent.cpp:321-325`）；
- agent 必须**原样回填 `id`**，controller 靠它匹配在途命令；
- 同一 agent 当前**一次只有一条在途命令**（`Controller.cpp:59-65,366-389`），controller 的
  `forward()` 用 `pending_id` 单槽等待；管理 HTTP 入口是单线程，所以实际上天然串行；
- agent 必须**按收到顺序**处理 command 并回 reply；回执可以比下一条命令晚，但不要乱序回不同 id。

### 3.7 白名单与身份指纹

- 白名单文件（默认 `agents.txt`，可用 `--agents` / `AGENTS_FILE` 改）：**每行一个 64 位小写 hex 公钥**；
- 匹配是**大小写敏感的字符串精确比较**（`Controller.cpp:224-227`）——登记大写指纹会永远被拒；
- 空文件 = 拒绝所有 agent；
- `vpn_controller --add-agent <hex>` 只是**追加写文件后退出**；运行中的 controller
  **不会热加载**，新指纹要重启 controller 才生效；
- agent 身份私钥默认 `keys/server_sig.key`（与 VPN 协议共用同一把 Ed25519 身份密钥），
  指纹 = 对应 `server_sig.pub` 的 64 hex。

### 3.8 断线重连（agent 侧责任）

| 项 | 值 |
|---|---|
| 首次退避 | 1000 ms |
| 退避增长 | ×2 |
| 封顶 | 60000 ms |
| 抖动 | 额外 +0..499 ms 随机 |
| 重置 | 每次成功握手后？**否**——代码只在进程启动时初始化，成功后不重置 |

> 实现参考 `Agent.cpp:230-239`。被 `reject`（未登记/签名失败）后同样走退避重试，
> 所以管理员登记指纹并重启 controller 后，agent 会自动接上，无需人工干预。

## 5. 客户端实现清单

### 5.1 管理客户端（HTTP 18081）

1. 每个请求新建 TCP 连接，发完整 HTTP 请求，读到对端关闭为止；
2. 必带 `Authorization: Bearer`；收到 401 先查 controller 令牌，再查 agent 的 `--token`；
3. `{id}` 来自 `GET /api/servers`，**原样使用**（不要自行拼名字）；id 只保证 `[A-Za-z0-9._-]`；
4. 请求体 ≤ 8KB；`list` 响应可能很大（见 6.1，约 950 个令牌触顶 64KB 帧）；
5. 503 = agent 离线（不排队，重试由用户决定）；504 = agent 10 秒没回；
6. 不要指望 `GET /` 有页面——当前 controller 只提供 JSON API。

### 5.2 第三方 agent 客户端（TCP 19090）

按顺序实现：

```
connect(controller:19090)
recv_frame()                    # 必须等到 challenge，不能先发
sig = Ed25519_sign(raw_nonce)   # nonce hex 先解码成 16 字节
send_frame({"type":"hello", ...})
recv_frame()                    # welcome 或 reject
loop:
    recv_frame(timeout=500ms)   # 有帧就处理 command
    每 15s send_frame({"type":"heartbeat"})
```

分帧伪代码（任何语言）：

```python
def send_frame(sock, obj):
    data = json.dumps(obj, ensure_ascii=False, separators=(',', ':')).encode('utf-8')
    assert len(data) <= 65536
    sock.sendall(len(data).to_bytes(4, 'big') + data)

def recv_exact(sock, n):
    buf = b''
    while len(buf) < n:
        chunk = sock.recv(n - len(buf))
        if not chunk:
            raise ConnectionError('closed')
        buf += chunk
    return buf

def recv_frame(sock):
    n = int.from_bytes(recv_exact(sock, 4), 'big')
    if n > 65536:
        raise ConnectionError('frame too large')
    return json.loads(recv_exact(sock, n))
```

三个必须处理的细节：

1. **半包**：长度头和载荷可能分多次 `recv` 到达，必须循环读满（`AdminWire.h:182-214` 就是为此写的）；
2. **一次 recv 可能带多帧**：要用缓冲（`Framer`），不能假设「一次 recv = 一帧」；
3. **发送 body 时转义**：`body` 是字符串字段，内部 JSON 的引号要转义一层。

### 5.3 握手校验（agent 自己也要防呆）

- controller 发来的 challenge 必须是 32 位 hex、解码后 16 字节；
- `welcome` 之前不要发送任何业务帧；
- `reject` 的 `reason` 直接打印给运维（`signature verify failed` / `pubkey not in whitelist`）。

## 6. 已知限制（对接前必读）

### 6.1 64KB 帧上限 → 令牌列表约 950 个触顶

一个令牌 67 字节（64 hex + 2 引号 + 1 逗号），加外层帧字段与转义，
`{"tokens":[...]}` 在约 **950~970 个令牌**时超过 65536 字节。
后果：agent 的 `send_frame` 返回 false → **agent 主动断开连接 → 退避重连**，
管理客户端收到 504 或连接错误。规避：一次不要堆积近千个未消费令牌（申请后尽快分发），
或二期给 `Framer`/`send_frame` 加分页/调大上限。

> 另注意：管理客户端自己也可能有上限。`server/ServerAdmin/ServerAdminClinet.cpp`
> 的 recvbuf 上限是 8KB，**约 120 个令牌**就会被它拒收。

### 6.2 `last_seen` 不是墙钟时间

见 2.4。不要格式化成年月日；二期改为 Unix ms。

### 6.3 controller 的 HTTP 入口是单线程、无读超时

`http_loop` 一次只服务一条连接，`recv` 是阻塞的（`Controller.cpp:404-451`）：
客户端连上后**必须尽快发完整请求**，否则会卡住其他管理请求。同理，慢客户端会拖住整个管理面。

另外，请求声明 `Content-Length` 超过 8KB 时 controller 回 413 后**立即 close**；
如果客户端在收到响应前仍在猛发 body，内核的 RST 可能把 413 冲掉（客户端看到连接重置）。
客户端应先发头、等响应，再决定是否继续发 body。

### 6.4 agent 通道是明文 TCP

握手能证明 agent 身份，但**不加密**：命令、令牌明文可被链路中间人看到。
当前仅适用于内网/VPN/防火墙白名单。计划书二期的 TLS 尚未实现。

### 6.5 无 Web 管理页 / 无 controller 侧限速 / 无审计

`server/Admin/web/index.html` 尚未做；controller 的 HTTP 入口没有鉴权失败限速、
没有审计日志（AdminServer 那边的五件套不覆盖 controller）。管理入口默认只绑环回。

### 6.6 `name` 必须唯一

controller 以 `id` 为键存 agent（`Controller.cpp:311-314`）。两个 agent 用同一个 `name`
时，后接入的会**顶掉**表项；旧连接不会立即关闭，会产生“幽灵连接”。
建议 `name` 用 `[A-Za-z0-9._-]{1,32}` 且全局唯一。

### 6.7 帧解析是“字段名查找”，不是真正 JSON 解析

`AdminWire.h` 的 `get_string`/`get_int` 按 `"key"` 第一次出现定位。
协议层的固定字段（type/id/method/path/body）由 controller 按固定顺序生成，所以安全；
但**第三方 agent 构造帧时建议也按此顺序**，且不要在额外字段里复用这些键名。

### 6.8 一期同时只能接一个 agent（多台服务器必读）

`Controller::agent_loop` 在 `accept` 之后直接进入该连接的心跳/命令循环，直到连接断开
才回到 `accept`（`Controller.cpp:237-356`）。实测行为：

- 第一台 agent 在线时，第二台 agent 的 TCP 连接能建立（内核 backlog），但 controller 不读；
- 第二台等 `challenge` 5 秒超时 → 断开 → 按退避重连，日志反复出现“未收到 challenge”；
- 第一台断开后，第二台在下一次重试时接入。

因此 **多台 VPN 服务器目前只能轮流在线**。客户端侧不需要特殊处理（真实 agent 会自动重连），
但部署时“第二台一直显示离线”是这一限制，不是配置错误。二期改为多连接（见第 9 节）。

## 7. 与计划书 3.5 的差异对照

| 项 | 计划书 3.5 | 当前代码 | 影响 |
|---|---|---|---|
| 传输 | TLS + 长度前缀 JSON 帧 | **明文 TCP** + 长度前缀 JSON 帧 | 必须内网/防火墙保护 |
| agent 端口 | 未定 | 19090 | — |
| 管理入口 | 管理 API + 静态 Web 页 | 极简 JSON API（18081），无 Web 页 | 管理客户端需要自己写 UI |
| 心跳 | 15s | agent 每 15s 发 heartbeat；controller 45s 判失联 | controller **不回 pong** |
| 命令帧 | `{"id","method","path","body"}` | 多一个 `"type":"command"` 字段 | 统一按 `type` 分发，兼容 |
| 回执帧 | `{"id","status","body"}` | 多一个 `"type":"reply"` 字段 | 同上 |
| 准入握手 | `hello` + Ed25519 签名 | controller 先下发 `challenge`，agent 再 `hello` | 多一次往返，防重放 |
| 白名单登记 | `add-agent <指纹>` | `--add-agent` 写文件，**需重启生效** | 无热加载 |
| 管理 API 寻址 | `/api/servers/{id}/...` | 同左 | 一致 |
| agent 离线 | 503 `agent offline` | 同左 | 一致 |
| 多服务器 | 二期 | **一期单 agent 连接**：id 机制已就绪，传输层未并发 | 第二台要等第一台断开（6.8） |

> 帧里多出的 `type` 字段是对计划书草案的补齐：草案只写了命令帧的形状，
> 未写控制帧；没有 `type` 就无法区分 challenge/heartbeat/command。

## 8. 构建与运行（当前未入 CMake）

两个可执行各自带 `main()`，需分开编译（`AdminWire.h` 是 header-only）：

```bash
cd /home/user/vscode/server

# 中转站
g++ -std=c++17 -Wall -Wextra -O2 -o build/vpn_controller \
    ServerAdmin/Controller.cpp Crypt/crypt.cpp -lcrypto -pthread

# agent（部署在每台 VPN 服务器）
g++ -std=c++17 -Wall -Wextra -O2 -o build/admin_agent \
    ServerAdmin/Agent.cpp Crypt/crypt.cpp -lcrypto -pthread
```

启动顺序与验证：

```bash
# 1) VPN 服务器本机：业务执行层
KEYS_DIR=keys ./build/admin_server          # 127.0.0.1:18080

# 2) 中转服务器：登记 agent 公钥指纹（小写 64hex），再启动
FP=$(python3 -c "import subprocess; d=subprocess.run(['openssl','pkey','-pubin','-in','keys/server_sig.pub','-outform','DER'],capture_output=True).stdout; print(d[-32:].hex())")
./build/vpn_controller --add-agent "$FP"
ADMIN_TOKEN=changeme ./build/vpn_controller --agent-bind 0.0.0.0 --http-bind 127.0.0.1

# 3) VPN 服务器：agent 反连
ADMIN_TOKEN=<admin_server 的管理令牌> \
./build/admin_agent --controller <controller-ip>:19090 \
                    --admin 127.0.0.1:18080 \
                    --key keys/server_sig.key \
                    --name hk-01

# 4) 管理端
curl -H "Authorization: Bearer changeme" http://127.0.0.1:18081/api/servers
```

> 指纹也可以用 `admin_server` 的 `/api/info` 的 `pubkey_hex` 字段抄下来——
> 两者是同一把 `server_sig.pub`。

## 9. 二期方向（写客户端时可预留）

1. **TLS**：controller 持证书，agent 校验证书/固定指纹；帧格式不变，只换传输层；
2. `last_seen` 改 Unix 毫秒，`GET /api/servers` 加 `online`/`version`/`connected_at`；
3. 令牌列表分页（`?offset=&limit=`），解决 64KB 触顶；
4. controller 侧限速（鉴权失败 5 次/分钟）与审计日志；
5. Web 管理页（计划书 5.1 的 `server/Admin/web/index.html`）挂到 18081；
6. 白名单热加载（SIGHUP）与 `--add-agent` 对运行中进程生效；
7. 命令并发：当前每 agent 单槽在途，二期可按 `id` 多槽并发；
8. **agent 通道并发**：每个 agent 连接一个线程或 poll 多连接，支持多台 VPN 服务器同时在线（当前一期单连接，见 6.8）。
