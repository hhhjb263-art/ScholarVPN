# ScholarVPN 更新系统设计

> 状态：**设计稿（未实现）**
> 日期：2026-10-19
> 读者：客户端开发者、发布负责人
> **范围：只覆盖客户端（Windows / Linux）。服务端升级由运维手动执行，不在本系统内（见第 6 章）。**
> 关联文档：`docs/客户端实现方案接口.md`（管理面接口）、`docs/ANDROID_PROTOCOL_SPEC.md`（线格式）

## 0. 一页纸速览

```
                     ┌──────────────────────────────┐
  发布机（离线/CI）   │ manifest.ini + .sig          │
                     │ 产物: setup.exe / client.tar │
                     └──────────────┬───────────────┘
                                    │ scp / rsync（不走 GitHub）
                                    ▼
                     ┌──────────────────────────────┐
                     │ 静态更新源（nginx）            │
                     │ https://dl/scholarvpn/...     │
                     └──────────────┬───────────────┘
                                    │ HTTPS GET
                                    ▼
                    ┌───────────────────────────────┐
                    │ 客户端（Windows / Linux）       │
                    │ 1 拉 manifest                  │
                    │ 2 验签 + 版本/灰度判定          │
                    │ 3 下载 + SHA256 校验            │
                    │ 4 停隧道（恢复路由 / DNS）       │
                    │ 5 交给 updater 替换             │
                    │ 6 重启 + 版本自检               │
                    └───────────────────────────────┘

  服务端不在本系统内：运维手动升级（第 6 章），不轮询、不自动下载、不自动替换。
```

| 决策点 | 结论 | 理由 |
|---|---|---|
| 更新范围 | **仅客户端**；服务端手动 | 服务端自动升级会断开全部在线会话，且要处理 systemd cgroup 自杀问题，收益不抵复杂度 |
| 清单格式 | **INI（复用 `src/platform/ini_doc.h`）** | 已单测 16 项；零新依赖；比手写 JSON 解析器省 200 行 |
| 清单签名 | **Ed25519 detached（`manifest.ini.sig`）** | `Crypt.cpp` 已有 `ed25519_verify`；与现有密钥体系同源 |
| 发布密钥 | **独立 `release_sig.key`，不进服务器** | 不该让每台 VPN 服务器都持有发布私钥 |
| 完整性校验 | **SHA-256（新增 20 行 `sha256_hex()`）+ 签名** | 签名保住"清单可信"，哈希保住"包没被换" |
| Windows 替换 | **调用现有 Inno Setup 静默安装** | 已有安装器；不另造自替换逻辑（DLL 一堆，容易半更新） |
| Linux 替换 | **A/B 目录 + `current` symlink 原子切换** | 回滚 = 再切一次 symlink，1 秒；不依赖包管理器 |
| 灰度 | **公钥哈希取模，无服务端状态** | 客户端没有遥测通道，不能依赖服务端读百分比 |
| 默认策略 | **检查开、自动装关** | 静默替换 VPN 客户端是高风险动作，必须用户/管理员确认 |

## 1. 现状与缺口

| 现状 | 证据 | 缺口 |
|---|---|---|
| 无版本资源 | `VPN_.rc` 只有 `IDI_ICON1`，无 `VERSIONINFO` | 资源管理器里看不到版本；updater 无法校验"装上的到底是不是新版本" |
| 版本号只有一处，还硬编码 | `ScholarVPN.iss:11 #define MyAppVersion "1.5"` | 代码里没有任何版本常量；改版本靠人肉 |
| 代码里无版本常量 | `grep -rn VERSION src/` 只命中 `NTDDI_VERSION` / `QT_VERSION` | 运行时无法上报/比较版本 |
| 无 SHA-256 导出 | `Crypt.cpp` 只把 SHA256 用在 HKDF 内部 | 无法校验下载包 |
| 客户端未启用网络模块 | `grep QNetwork src/` 为空（但 iss 打包了 `Qt6Network.dll`） | 没有下载能力 |
| 安装器已就绪 | `scripts/package.bat`：MSBuild → windeployqt → ISCC | 可作为 Windows 更新的执行体 |
| 服务端 systemd 就绪 | `server/vpn-server.service` + `start.sh install` | 手动升级的落点（`systemctl restart`），本系统不接管 |
| 服务端无下载工具依赖 | `start.sh` 里没有 curl/wget/python | 手动升级直接 `scp` 传包，不需要下载能力 |
| 管理面有 HTTP API | `AdminServer` 的 `/api/info` 返回 `version/ip/port/pubkey` | `version` 目前恒为 `"1.0"`，是接口版本而非程序版本；建议补 `app_version` 便于人工核对 |

**结论**：更新系统需要先补"版本单一来源"，再谈分发。

## 2. 目标与非目标

**目标**

1. 客户端（Windows / Linux）能发现新版本、下载、校验、替换、重启，失败可回滚。
2. 全链路防篡改：清单签名 + 包哈希；防降级、防重放。
3. 支持灰度（按客户端身份取模）与紧急撤销（`Revoked` 列表）。
4. 不引入新的运行时依赖（Windows 不加 DLL，Linux 不加包）。
5. 发布产物与清单可审计：每次发布都能追到"哪个版本、什么哈希、谁签的"。

**非目标（v1 明确不做）**

- **不做服务端自动更新**。服务端由运维手动升级（第 6 章），本系统不轮询、不下载、不替换服务端二进制。
- 不做静默强制升级（`AutoInstall=0` 是默认值）。
- 不做增量差分包（体积不是瓶颈；差分带来版本矩阵爆炸）。
- 不做服务端"零断线"热升级（需要 `SO_REUSEPORT` 双进程交接，收益不抵复杂度）。
- 不做 P2P/CDN 分发。
- 不做 Android 自更新（应用商店渠道，另行处理）。

## 3. 版本号：单一来源

### 3.1 新增 `src/version.h`

```cpp
#pragma once
// ============================================================================
// 版本号唯一来源。改版本只改这里，其它地方全部引用宏：
//   - VPN_.rc          → FILEVERSION / ProductVersion（资源管理器可见）
//   - ScholarVPN.iss   → ISPP GetFileVersion() 直接读 exe，不再手写
//   - 运行时           → ClientApp / vpn_server 启动日志、更新检查
// ============================================================================

#define SCHOLARVPN_VER_MAJOR 1
#define SCHOLARVPN_VER_MINOR 6
#define SCHOLARVPN_VER_PATCH 0

// 用字符串字面量（含引号），这样 RC 与 C++ 两边都能直接用
#define SCHOLARVPN_VER_STRING "1.6.0"

// 隧道线格式版本：只在"报文布局/握手字段"变更时递增。
// 与 tunnel_protoco.h 的 v_udp/v_tcp 不同——后者是传输标识，不是协议代次。
// 服务端与客户端不一致时，靠发布流程保证（先升服务端再发客户端清单），
// 更新系统只比较客户端版本，不读取服务端协议版本。
#define SCHOLARVPN_PROTO_VERSION 1
```

### 3.2 `VPN_.rc` 补版本资源

```rc
#include "resource.h"
#include "src/version.h"

VS_VERSION_INFO VERSIONINFO
 FILEVERSION SCHOLARVPN_VER_MAJOR,SCHOLARVPN_VER_MINOR,SCHOLARVPN_VER_PATCH,0
 PRODUCTVERSION SCHOLARVPN_VER_MAJOR,SCHOLARVPN_VER_MINOR,SCHOLARVPN_VER_PATCH,0
 FILEFLAGSMASK 0x3fL
 FILEFLAGS 0x0L
 FILEOS 0x40004L
 FILETYPE 0x1L
 FILESUBTYPE 0x0L
BEGIN
    BLOCK "StringFileInfo"
    BEGIN
        BLOCK "080404b0"
        BEGIN
            VALUE "CompanyName",      "ScholarVPN"
            VALUE "FileDescription",  "ScholarVPN Client"
            VALUE "FileVersion",      SCHOLARVPN_VER_STRING
            VALUE "ProductName",      "ScholarVPN"
            VALUE "ProductVersion",   SCHOLARVPN_VER_STRING
        END
    END
    BLOCK "VarFileInfo"
    BEGIN
        VALUE "Translation", 0x804, 1200
    END
END
```

### 3.3 `ScholarVPN.iss` 去掉手写版本

```iss
; 编译前 exe 已存在（package.bat 顺序保证），直接读文件版本，永不与代码脱节
#define MyAppVersion GetFileVersion("x64\Release\ScholarVPN.exe")
```

> ISPP 的 `GetFileVersion` 在文件不存在时返回空串。`package.bat` 里已在 ISCC 之前完成编译，顺序天然满足；若单独跑 ISCC，需先编译。
> 它返回的是四段格式（`1.6.0.0`），Inno 只用于显示与注册表 `DisplayVersion`，多一个 `.0` 无碍；要三段显示可在 ISPP 里 `StringChange` 裁掉尾段。

### 3.4 服务端版本

`server/main.cpp` 启动日志打印 `SCHOLARVPN_VER_STRING`，并新增 `--version` 参数（打印后退出）。`AdminServer` 的 `/api/info` 增加 `app_version` 字段（`version` 保留为接口版本 `"1.0"`，避免破坏现有管理端）。

> 这两个东西**只服务于人工核对**：手动升级后 `curl /api/info` 或 `vpn_server --version` 确认装对了版本。
> 更新系统不读取、不轮询服务端版本。

## 4. 更新清单（manifest）

### 4.1 格式：INI

```ini
; https://dl.example.com/scholarvpn/manifest.ini
[Manifest]
Schema=1
Channel=stable
Generated=1792540800          ; Unix 秒。客户端只接受 >= 上次见过的值（防重放旧清单）
Revoked=1.5.0,1.5.2           ; 命中即强制处理（见 7.3）

[windows-x64]
Version=1.6.0
URL=https://dl.example.com/scholarvpn/ScholarVPN-1.6.0-setup.exe
SHA256=9f2c8a41d0b7e3f5a6c9d1e8b4f7a2c5d8e1f4a7b0c3d6e9f2a5b8c1d4e7f0a3
Size=48213000
MinFrom=1.0.0
Notes=修复 TLS 证书校验；TCP 分帧性能优化
Rollout=100

; 平台节只描述【客户端】。服务端二进制不进清单（服务端手动升级，见第 6 章）
[linux-x64]
Version=1.6.0
URL=https://dl.example.com/scholarvpn/scholarvpn-1.6.0-linux-x64.tar.gz
SHA256=3b7e1d9c5a2f8b4e6d0c9a7f3e1b5d8c2a4f6e9b1d3c5a7f0e2b4d6c8a1f3e5
Size=6124000
MinFrom=1.0.0
Notes=新增 Linux 客户端；路由改为 0.0.0.0/1 + 128.0.0.0/1
Rollout=20
```

**为什么是 INI 而不是 JSON**：项目里 JSON 全是手写拼接（`AdminServer`），没有解析器。清单是"多平台 × 固定字段"，INI 的节天然对应平台，且 `ini_doc.h` 已通过 16 项单测（含 UTF-16 BOM、注释保留、大小写不敏感）。引入 JSON 解析器要多 200 行 + 一堆边界用例，不值得。

### 4.2 签名文件

`manifest.ini.sig`：**base64 编码的 Ed25519 裸签名**（对 `manifest.ini` 原始字节签名，不做哈希预处理——Ed25519 内部已是 SHA-512）。

```bash
# 生成发布密钥（只做一次，私钥离线保管）
openssl genpkey -algorithm ED25519 -out keys/release_sig.key
openssl pkey -in keys/release_sig.key -pubout -out keys/release_sig.pub

# 每次发布：签名清单
openssl pkeyutl -sign -inkey keys/release_sig.key -rawin \
        -in manifest.ini -out manifest.ini.sig.raw
base64 -w0 manifest.ini.sig.raw > manifest.ini.sig
```

客户端内置 `release_sig.pub` 的 PEM，与 `ClientApp.cpp` 里 `kServerSigPubPem` 并列：

```cpp
// 发布签名公钥：只用于验证更新清单，绝不从 config.ini 读
// （允许配置就等于取消了签名——攻击者把 URL 指向自己的清单即可）
static const char kReleaseSigPubPem[] = R"(-----BEGIN PUBLIC KEY-----
MCowBQYDK2VwAyEA...（替换为真实的 release_sig.pub 正文）
-----END PUBLIC KEY-----
)";
```

### 4.3 字段语义

| 字段 | 类型 | 语义 |
|---|---|---|
| `Schema` | int | 清单格式版本。客户端只认自己支持的值，≥2 且不认识则整份拒绝（不猜） |
| `Channel` | string | `stable` / `beta`。与客户端 `[Update] Channel` 不一致则忽略 |
| `Generated` | int64 | Unix 秒。`<` 本地已记录的 `last_seen` 视为重放，拒绝 |
| `Revoked` | list | 逗号分隔版本号。当前版本命中 → 即使 `Version` 不更高也要处理（用于撤回坏版本） |
| `Version` | semver | 目标版本，必须严格 `>` 当前版本才提示（`Revoked` 例外） |
| `URL` | https | 必须是 `https://`（v1 拒绝明文 http，避免"首次下载被替换"） |
| `SHA256` | hex64 | 包哈希，下载后强校验 |
| `Size` | int64 | 预期字节数；用于提前拒绝异常小/大的响应（防半截或黑洞） |
| `MinFrom` | semver | 当前版本 `<` 此值时不允许热更新（数据结构/配置不兼容，需手动重装） |
| `Notes` | string | 单行更新说明，GUI 直接展示（限 200 字符，超出截断） |
| `Rollout` | 0-100 | 灰度百分比。`bucket(identity) >= Rollout` 时本轮跳过 |

## 5. 客户端更新流程

### 5.1 状态机

```
Idle
 ├─(定时器/手动)──> Checking ──(无更新/被灰度跳过)──> Idle
 │                      │
 │                      ├─(需要更新)──> Available ──(用户取消)──> Idle
 │                      │                    │
 │                      │                    └─(确认)──> Downloading
 │                      │                                   │
 │                      │                          (哈希不符)→ Failed(可重试)
 │                      │                                   ▼
 │                      │                              Verifying(签名已验过清单，此处只验包)
 │                      │                                   ▼
 │                      └──────────────────────────> Installing
 │                                                           │
 │                                        (先 stop()：断开 + 恢复路由/DNS)
 │                                                           ▼
 │                                                   HandoffToUpdater
 │                                                  （主程序退出，updater 接手）
 └───────────────────────────────────────────────────────────┘
```

### 5.2 三个不可省略的顺序细节

1. **安装前必须走 `ClientApp::stop()`**，不能直接 `ExitProcess`。
   `stop()` 会 `m_mgr->stop()` → `m_route->clear_routes()` → `m_dnsGuard.restore()`。
   直接杀进程只靠 DNS 看门狗兜底，**路由条目会残留**（Wintun 是持久设备），用户更新完电脑可能直接没网。
2. **updater 必须等主进程真正退出**再替换文件（Windows 文件占用；Linux 可替换运行中的二进制，但为一致性统一等待）。
3. **替换后必须回读新版本号**（`GetFileVersionInfoW` / 二进制内嵌版本串），不能"安装器返回 0 就当成功"。

### 5.3 Windows

```
ScholarVPN.exe（Qt GUI，普通权限运行）
   │ 发现更新 → 下载到 %LOCALAPPDATA%\ScholarVPN\update\ScholarVPN-1.6.0-setup.exe
   │ 校验 SHA256（新增 sha256_hex，EVP_Digest 单次）
   │ ClientApp::stop()   ← 断开 + 清路由 + 恢复 DNS
   ▼
ShellExecuteExW(open, "vpn_updater.exe", ...)        ← 普通权限，此处不弹 UAC
   │ 只有"启动成功、拿到进程句柄"之后才 ExitProcess
   ▼
vpn_updater.exe（独立小 exe：无 Qt、不链接 OpenSSL，哈希走系统自带 BCrypt）
   1. OpenProcess + WaitForSingleObject(wait-pid)      等主进程退出（超时 15s 强杀）
   2. 复算 SHA256（BCryptOpenAlgorithmProvider + BCryptHashData，约 60 行）
      不符 → 删除包 + 退出码 3
   3. ShellExecuteExW(open, setup.exe,
        "/SILENT /SUPPRESSMSGBOXES /NORESTART /CLOSEAPPLICATIONS /LOG")
       ← Inno 自带 requireAdministrator，UAC 在这一步弹（全程仅一次）
   4. 等安装器退出；取返回码（1223/1602 = 用户取消 UAC）
   5. 读 {app}\ScholarVPN.exe 的 FILEVERSION，与 --expect 比较
   6. 成功 → 重启主程序；失败 → 保留旧安装（Inno 已回滚）+ 写日志到
      %LOCALAPPDATA%\ScholarVPN\update\updater.log + 重新拉起旧版本
```

> updater 刻意不链接 `libcrypto`：它运行在"主程序已退出、安装包尚未落地"的窗口期，
> 依赖越少越不容易因为 DLL 被占用/缺失而卡死。Windows CNG（`bcrypt.lib`）是系统自带，
> 零分发成本。

**为什么用 Inno 而不是自替换**：安装目录里有 Qt DLL、插件目录、`wintun.dll`、`style.qss`。只替换 exe 会出现"新 exe + 旧插件"的混搭，Qt 版本不匹配直接启动失败。Inno 的 `/CLOSEAPPLICATIONS` 会正确处理文件占用，且安装失败自动回滚。

**不要用 PowerShell / .bat 包一层**

```powershell
# 绝对不要写这种东西
Start-Process -FilePath "$env:TEMP\setup.exe" -ArgumentList "/SILENT" -Verb RunAs
```

三个理由：

1. **EDR 最敏感的形态**："脚本解释器 → 执行刚下载的 exe"是恶意软件的经典起手式。企业环境大概率直接拦，
   个人机器也可能弹警告，让用户以为中了病毒。
2. **环境不确定性**：执行策略（`ExecutionPolicy`）、PowerShell 5.1 与 7 的差异、编码、路径含空格或中文，
   任意一个都能让更新"在某些机器上就是跑不起来"，而且日志里看不出来。
3. **拿不到可靠的退出码与等待语义**：脚本壳的返回值经常是 0，即使安装器已经失败。

正确做法是 `ShellExecuteExW` + `SEE_MASK_NOCLOSEPROCESS`，拿进程句柄直接等。20 行代码，行为确定：

```cpp
SHELLEXECUTEINFOW sei{};
sei.cbSize       = sizeof(sei);
sei.fMask        = SEE_MASK_NOCLOSEPROCESS | SEE_MASK_FLAG_NO_UI;
sei.lpFile       = cmd;            // "vpn_updater.exe"
sei.lpParameters = params;         // "--pkg ... --wait-pid ..."
sei.lpDirectory  = dir.c_str();
sei.nShow        = SW_HIDE;        // 更新器无界面，避免黑框一闪
if (!::ShellExecuteExW(&sei)) {
    return false;                  // 失败就保持主程序运行，别退
}
// 不要在这里 ExitProcess —— 先确认 sei.hProcess 有效
```

> 顺带一提：`DnsLeakGuard.cpp` 现在用 PowerShell 派生崩溃看门狗（`spawn_crash_watchdog`），
> 同样踩上面第 1、2 条风险。后续可以换成"小 helper exe 等父进程句柄"，与 updater 同一套思路。

**UAC 只弹一次**：`vpn_updater.exe` 用 `asInvoker`（最小权限），提权交给 Inno 安装器自己
（`ScholarVPN.iss` 里 `PrivilegesRequired=admin`）。用户全程只在安装器启动那一刻看到一次 UAC，
而不是"updater 一次 + 安装器一次"两次。

**用户取消 UAC 必须能退回来**：Inno 返回 1223（`ERROR_CANCELLED`）或 1602 时，updater 要
① 写日志、② 重新拉起**旧版本**主程序。否则用户看到的是"点了更新，程序没了"——这比更新失败本身严重得多。
主程序侧同理：`ShellExecuteExW` 未成功返回之前**不许** `ExitProcess`。

### 5.4 Linux

```
/opt/scholarvpn/
├── releases/
│   ├── 1.5.2/vpn_client
│   └── 1.6.0/vpn_client          ← 新版本解包到这里
├── current -> releases/1.6.0     ← 唯一对外入口（symlink）
└── update/updater.log
```

`vpn_client` 通过 `argv[0]` 解析自身真实路径（`readlink /proc/self/exe`），不硬编码版本目录。

```bash
# 核心三步（vpn_client --update 内部；Linux 客户端自带，不额外发脚本）
tar -xzf "$PKG" -C "/opt/scholarvpn/releases/$VER/"     # 1. 解包
ln -sfn "releases/$VER" /opt/scholarvpn/.current.tmp     # 2. 原子切换
mv -T /opt/scholarvpn/.current.tmp /opt/scholarvpn/current
systemctl restart scholarvpn-client                      # 3. 重启（system 或 --user）
```

`mv -T` 是原子替换 symlink 的关键；直接 `ln -sfn` 在某些情况下会产生"目录里再建一个链接"的坑。

**替换后自检**：`/opt/scholarvpn/current/vpn_client --version` 必须输出目标版本，否则视为安装失败（`tar` 解开成功不等于二进制能跑，缺 `libcrypto.so.3` 时只有执行才发现）。

**权限**：客户端若以 `systemd --user` 运行，更新用 `systemctl --user`；若以 system service 运行（root），更新需 `sudo` 或 polkit 授权。v1 要求显式 `sudo /opt/scholarvpn/current/vpn_client --update`，不做自动提权（不在 GUI 里偷偷调 `pkexec`）。

### 5.5 更新检查时机

| 触发 | 行为 |
|---|---|
| 启动后 30 秒（首次） | 静默检查；有更新只在托盘/GUI 角标提示，不弹模态框 |
| 每 `CheckIntervalHours`（默认 24h） | 同上 |
| GUI「检查更新」按钮 | 立即检查，结果用对话框展示（含 Notes） |
| 连接中 | **不检查**（避免下载流量走隧道，白白占用用户带宽） |

第 4 条容易被忽略：更新包几 MB，走隧道会占用本就很窄的国际带宽（参见 `docs/TODAY.md` 里 ~1 Mbps 的实测），必须在隧道断开状态下下载。

## 6. 服务端：手动升级（明确不在本系统内）

> 一句话：**更新系统只做客户端**。服务端升级是一次人工操作，本章只规定"怎么升才安全"，
> 不产出脚本、不装定时器、不做自动回滚。

### 6.1 为什么不自动

| 理由 | 具体后果 |
|---|---|
| 会断开全部在线会话 | `systemctl restart vpn-server` 清空所有 `Session`，客户端要退避重连 3~10 秒。自动升级等于"随机时间把用户踢下线" |
| 会杀掉自己 | `vpn-server.service` 是 `Type=simple`，在其 cgroup 内执行 `systemctl restart` 会连带终止执行重启命令的进程。规避方案（另起独立 unit）等于多维护一个常驻组件 |
| 升级频率极低 | 服务端只在协议或转发逻辑变更时升级，通常几个月一次。为这个频率建自更新链路不划算 |
| 出错代价最高 | 服务端升坏 = 全体用户连不上。人工在场能立刻回滚，自动化只会把事故放大 |

### 6.2 目录布局（手动升级也按这个放，回滚最省事）

```
/opt/scholarvpn/
├── releases/
│   ├── 1.5.2/vpn_server
│   └── 1.6.0/vpn_server
├── current -> releases/1.6.0        # systemd 与 start.sh 都指向这里
├── keys/                            # 绝不放进 release 目录
└── logs/
```

`vpn-server.service` 的 `ExecStart=__SCRIPT_DIR__/start.sh start`，把 `start.sh` 里启动二进制的路径改成
`$ROOT/current/vpn_server` 即可享受"切 symlink 即回滚"。

### 6.3 手动升级清单（照抄执行，不是脚本）

```bash
VERSION=1.6.0
ROOT=/opt/scholarvpn

# 1. 本地先核对：清单里的哈希必须与包一致（清单本身已由发布方签名，离线核对即可）
sha256sum scholarvpn-server-$VERSION.tar.gz

# 2. 传包（不经过 GitHub，直接 scp）
scp scholarvpn-server-$VERSION.tar.gz root@vpn-host:/var/cache/

# 3. 解包到新目录（不动 current）
ssh root@vpn-host "mkdir -p $ROOT/releases/$VERSION && \
    tar -xzf /var/cache/scholarvpn-server-$VERSION.tar.gz -C $ROOT/releases/$VERSION"

# 4. 新二进制自检（能跑起来、能读到库）
ssh root@vpn-host "$ROOT/releases/$VERSION/vpn_server --version"

# 5. 切换（原子）
ssh root@vpn-host "ln -sfn releases/$VERSION $ROOT/.current.tmp && \
    mv -T $ROOT/.current.tmp $ROOT/current"

# 6. 重启 + 健康检查（进程活着 + UDP 端口真的在听）
ssh root@vpn-host "systemctl restart vpn-server && sleep 2 && \
    systemctl is-active --quiet vpn-server && \
    ss -lun | grep -q ':$VPN_PORT ' && echo OK"

# 7. 失败回滚（把 symlink 切回去再起）
ssh root@vpn-host "ln -sfn releases/1.5.2 $ROOT/.current.tmp && \
    mv -T $ROOT/.current.tmp $ROOT/current && systemctl restart vpn-server"
```

**健康检查为什么不能只看 `is-active`**：进程没退但端口没起来（密钥缺失、TUN 创建失败）照样是 `active (running)`。
必须确认 UDP 监听真的存在，最好再用一台客户端实际连一次。

### 6.4 不丢数据的三条硬约束

1. `keys/`（`server_sig.key`、`registered_clients.txt`、`register_tokens.txt`）**不在 release 目录内**。
   否则切版本后已注册客户端全部要重新注册。
2. `/etc/default/vpn-server`（systemd `EnvironmentFile`）不动。
3. `logs/` 不动，保持固定路径。

### 6.5 与客户端发布的顺序

**永远先升服务端，再发客户端清单。** 反过来会出现"新客户端连旧服务端"——握手在 `UDP.cpp:444`
的 `hdr.version` 校验处被丢弃，用户只看到"连不上"，服务端日志里连一条有效的认证记录都没有。

## 7. 灰度 / 回滚 / 防降级 / 防重放

### 7.1 灰度（无服务端状态）

```cpp
// 用客户端身份公钥做桶：同一台机器永远落在同一个桶，不会"时有时无"
static uint32_t bucket_of(const std::string& identity_pub_b64)
{
    uint32_t h = 2166136261u;                      // FNV-1a
    for (unsigned char c : identity_pub_b64) { h ^= c; h *= 16777619u; }
    return h % 100u;
}

bool in_rollout(const UpdateEntry& e, const std::string& pub)
{
    return static_cast<int>(bucket_of(pub)) < e.rollout;
}
```

`Rollout=20` 意味着约 20% 的客户端会看到更新。逐步提到 50 → 100。不需要服务端记录谁升了级——这也是它能在没有遥测的前提下工作的原因。

### 7.2 防降级

- 正常路径：`Version` 必须严格大于当前版本。
- 例外：当前版本出现在 `Revoked` 里，允许"降级"到 `Version`（撤回坏版本）。此时要求 `Version != current` 即可，不要求更高。

### 7.3 防重放

客户端在 `config.ini` 记录：

```ini
[Update]
LastSeenGenerated=1792540800
```

拉到的清单 `Generated < LastSeenGenerated` → 直接丢弃并记日志（可能有人在重放旧清单把你"降级"到有漏洞的版本）。成功处理后写回新值。

> 注意：这条只防"重放旧清单"，不能防"攻击者伪造清单"——后者由签名解决。

### 7.4 回滚

| 场景 | 手段 |
|---|---|
| 服务端新版起不来 | **人工**切回上一 symlink 再 restart（6.3 第 7 步），本系统不参与 |
| 客户端新版发现缺陷 | 把 `manifest` 的 `Version` 指回旧版 + 把坏版本写进 `Revoked` → 客户端"降级"回去 |
| 客户端升级后崩溃 | 不做自动回滚（无法自证崩溃）；靠 `Revoked` 人工撤 |

## 8. 安全模型

| 威胁 | 对策 | 残留风险 |
|---|---|---|
| 更新源被入侵，替换安装包 | 清单签名 + 包 SHA-256 | 若发布私钥也泄露则失效 → 私钥离线/HSM |
| MITM 替换清单 | Ed25519 验签（公钥内置，不可配置） | 无 |
| MITM 替换安装包 | SHA-256 与签名清单绑定 | 无 |
| 降级到含漏洞的旧版 | 版本单调 + `Generated` 单调 + `Revoked` | 用户手动安装旧包不受控（属预期） |
| 用户把 `ManifestURL` 指向恶意源 | 签名公钥内置 → 只能导致"更新失败" | 无（仅拒绝服务） |
| 明文 HTTP 被劫持 | `URL` 字段强制 `https://` | 证书信任依赖系统 CA |
| 半更新（新 exe + 旧 DLL） | Windows 走完整安装器；Linux 走整目录 | 无 |
| 杀软拦截 updater | updater 单独签名（可选）；不落地 `.bat`/`.ps1` | 企业环境白名单需人工 |
| 更新过程中断网导致隧道残留路由 | 安装前强制 `ClientApp::stop()` | 进程被强杀时仍靠 DNS 看门狗兜底 |

**发布私钥管理**：

- `keys/release_sig.key` **绝不进仓库**（`keys/*` 已在 `.gitignore`）；建议放离线介质或 CI 的 secret store。
- 私钥泄露 → 换密钥 + 客户端内置新公钥 → 需要一次"手动/带外"升级才能恢复自动更新链路。这个恢复路径要写进运维手册。

## 10. 发布流水线

```bash
#!/usr/bin/env bash
# tools/release/publish.sh —— 三步：打包、签名清单、同步（不走 GitHub）
set -euo pipefail

VERSION=$(grep SCHOLARVPN_VER_STRING src/version.h | cut -d'"' -f2)
STAGE=$(mktemp -d)
REMOTE="user@dl.example.com:/srv/dl/scholarvpn"

# 1. 客户端产物（唯一进清单的东西）
./scripts/package.bat                                  # Windows 客户端安装包
tar -czf "$STAGE/scholarvpn-$VERSION-linux-x64.tar.gz" -C build vpn_client vpn_updater

# 1b. 服务端包：单独产出、不进清单、由运维手工部署（第 6 章）
tar -czf "$STAGE/scholarvpn-server-$VERSION.tar.gz" -C build-server vpn_server

# 2. 哈希 + 清单（保留其它平台的已有条目）
for f in "$STAGE"/*; do echo "$(sha256sum "$f" | cut -d' ' -f1)  $(basename "$f")"; done

# 3. 签名（私钥从离线介质/CI secret 取，切勿提交）
openssl pkeyutl -sign -inkey "$RELKEY" -rawin \
        -in "$STAGE/manifest.ini" -out "$STAGE/manifest.ini.sig.raw"
base64 -w0 "$STAGE/manifest.ini.sig.raw" > "$STAGE/manifest.ini.sig"

# 4. 同步（用户明确要求：部署直接文件同步，不走 GitHub）
scp "$STAGE"/* "$REMOTE/pending/"
# 人工核对后在服务器上把 pending/ 原子 mv 到 live/（避免客户端读到半更新的清单）
```

**发布顺序铁律**：

1. 先出服务端包 → 运维按第 6 章**手动**升上去并验证；
2. 再上传客户端清单（此时客户端才可能升到新版本）。

反过来会出现"新客户端连旧服务端"，握手在 `hdr.version` 校验处被丢弃（`UDP.cpp:444`），
用户只看到"连不上"，服务端日志里连有效的认证记录都没有。
服务端包与客户端包建议用同一个 `VERSION`，方便人工核对（虽然它们各自独立升级）。

## 11. 分阶段落地

| 阶段 | 内容 | 验收 |
|---|---|---|
| P0（0.5 天） | `version.h` + `VPN_.rc` + `iss` 读文件版本 + `sha256_hex` | 属性页能看到 1.6.0；`sha256_hex("abc")` 等于已知值 |
| P1（1 天） | `UpdateManifest`（解析/验签/比较/灰度）+ 单测 | 伪造签名被拒；降级被拒；`Rollout=0` 永远不推 |
| P2（1.5 天） | `UpdateChecker` + 两个平台的 HTTP GET + 下载校验 | 断网/404/哈希不符分别给出明确错误；半截包被拒 |
| P3（1.5 天） | Windows updater（等父进程 → Inno 静默 → 回读版本） | 从 1.5.2 升到 1.6.0；中途取消不留半装 |
| P4（1.5 天） | Linux A/B + symlink + systemd | 升级后 `current` 指向新目录；故意放坏包能自动回滚 |
| P5（1 天） | GUI 入口 + 托盘提示 + 文档 | 检查更新有进度、失败原因可读 |

**总工期约 7 天**（单人对齐现有代码风格）。P0/P1 可以立刻做，不依赖任何平台层改造。
服务端升级不在工期里——它是第 6 章那几条手工命令，不写代码。

## 12. 验收用例（必须逐条过）

1. 清单签名错误 → 客户端拒绝，日志明确写"验签失败"，不提示更新。
2. 清单 `Version` 低于当前 → 不提示（除非命中 `Revoked`）。
3. 清单 `Generated` 比上次小 → 拒绝并记"疑似重放"。
4. 包 SHA-256 不符 → 删除已下载文件，可重试。
5. 下载到一半断网 → 不进入安装态，`.part` 文件清理。
6. 灰度 `Rollout=20` → 同一台机器多次检查结果一致（桶稳定）。
7. Windows 更新时 VPN 正在连接 → 自动断开、路由恢复、DNS 恢复，再安装。
8. Windows 更新被 UAC 取消 → 主程序仍在运行，隧道可重连，不处于半死状态。
9. Linux 升级后进程崩溃 → 15 秒内自动回滚，`systemctl is-active` 恢复。
10. 手动把 `ManifestURL` 改成恶意地址 → 只能失败，不会安装任何东西。
11. 服务端按第 6 章手动升级 → `keys/registered_clients.txt` 未变，已注册客户端无需重新注册。

## 13. 已知限制 / 未决问题

1. **协议版本不协商**：服务端不回传自己的 `SCHOLARVPN_PROTO_VERSION`。更新系统只能靠 `MinFrom` + 发布顺序约束，无法在运行时判定"能不能连"。建议 v2 在 `m_identity_ok` 里追加一个字节的服务端协议版本（需要动线格式，属于破坏性变更）。
2. **服务端版本靠人工核对**：服务端手动升级，升级后有多少客户端重连成功只能看 `/api/info` 的 `app_version` 与服务端日志里的 `[AUTH]` 计数，没有自动比对。
3. **企业批量部署**：`AutoInstall=1` 只是"下载完直接装"，没有集中策略下发。真正的批量部署应走组策略/Intune/Ansible，不在本项目范围。
4. **Linux 客户端更新权限**：`sudo` 交互无法在 GUI 里优雅完成。若后续坚持 GUI 体验，需要引入 polkit helper（`org.scholarvpn.update` action），这是额外 1~2 天工作量。
5. **回滚的触发是"人工判定"**：目前没有自动"新版连续崩溃 N 次就回滚"的机制（客户端崩溃无法自证）。若要实现，需要外部看门狗（Windows 计划任务 / systemd `StartLimitAction`）记录启动失败次数。
