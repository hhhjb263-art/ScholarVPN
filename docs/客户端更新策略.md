# 客户端更新策略（服务端决策）

> 状态：**设计稿（未实现）**
> 日期：2026-10-27
> 关联：`docs/更新系统设计.md`（清单格式 / 签名 / 安装器，仍然复用）
> 范围：客户端版本上报、服务端更新决策接口、GUI 更新入口、强制更新约束

---

## 0. 一页纸

**需求**：客户端加「检查更新」按钮；**每次启动**都要向服务端校验；由**服务端**决定「强制更新 / 可选更新 / 无需更新」。

**与旧设计的区别**：

| | 旧（仅静态清单） | 新 |
|---|---|---|
| 谁决定要不要升 | 客户端比较版本号 | **服务端下策略** |
| 强制与否 | 客户端配置项 | **服务端按 min_version 判定** |
| 校验时机 | 启动 + 24h 定时 | **每次启动必查** + 按钮手动查 |
| 服务端参与 | 只托管文件 | **新增决策接口** |

**核心取舍**：服务端只下「该不该升、多急」，**包地址与哈希仍来自签名清单**——决策接口被劫持最多让用户多点几次“更新”，不能让它指定下载源。

| 决策点 | 结论 | 理由 |
|---|---|---|
| 决策接口 | 服务端 `AdminServer` 新增 `GET /api/client/update` | 已有 HTTP 服务，零新增端口 |
| 响应可信性 | **Ed25519 签名**（复用 `release_sig.key`） | 响应里含 `forced`，可伪造就等于可诱导用户装任何东西 |
| 版本上报方式 | 查询参数 `?ver=&os=` | 无状态，服务端不需要存客户端清单 |
| 启动校验时机 | GUI 起来后立刻查一次（**直连**，不走隧道） | 此刻隧道还没建立，走隧道不可能 |
| 查不到怎么办 | **放行**，记日志，下次启动再试 | 否则服务端一挂，全体客户端都开不了 |
| 强制更新的执行 | 客户端禁用连接 + 不可关闭弹窗；**服务端同时拒绝该版本认证** | 只有客户端自觉 = 形同虚设 |
| 更新包下载 | 公网直连（不走隧道） | 要替换自己，不能依赖自己要替换的隧道 |

## 1. 为什么不能只靠静态清单

静态清单能回答「最新版是什么」，但回答不了「**这一版还能不能用**」。而后者是运营问题：

- 协议有破坏性变更（线格式升到 v3）→ 旧客户端连上也是握手失败，用户只会看到“连不上”，反复重试；
- 发现严重漏洞（比如认证可绕过）→ 必须让旧版本彻底下线，而不是“提示一下”；
- 灰度/回滚 → 需要按版本精确控制谁能连。

这些判断依赖服务端当下的状态（在线客户端版本分布、事故等级），静态清单没法表达。所以需要服务端参与决策。

## 2. 整体架构

```
┌─────────────── 客户端启动 ───────────────┐
│ 1. 读本地版本        (SCHOLARVPN_VER_STRING)      │
│ 2. GET update-policy.ini + .sig（静态源）          │
│ 3. 验签响应（内置 release 公钥）                  │
│ 4. 按 action 决定 UI：                            │
│      none     → 正常进入                          │
│      optional → 顶部提示条 + 更新按钮红点          │
│      forced   → 阻塞弹窗，只能更新或退出           │
└───────────────────────────────────────────┘
                     │
                     ▼
┌─────────────── 服务端决策 ────────────────┐
│ 读配置：latest / min / notes / 下载地址            │
│ ver <  min      → forced                          │
│ min <= ver < latest → optional                    │
│ ver >= latest   → none                            │
│ 签名响应（Ed25519）                               │
└───────────────────────────────────────────┘
                     │
                     ▼
┌─────────────── 更新执行 ──────────────────┐
│ 仍走 docs/更新系统设计.md 的路径：                │
│ 下载 → SHA-256 校验 → 停隧道 → 安装器 → 重启      │
└───────────────────────────────────────────┘
```

**两条独立通道**：

- **决策通道**：轻量 HTTP 查询，明文即可（响应自带签名）；
- **产物通道**：`manifest.ini` + `.sig` + 安装包，走静态源。

## 3. 版本上报

### 3.1 版本从哪来

必须先落 P0：`src/version.h`

```cpp
#define SCHOLARVPN_VER_MAJOR 1
#define SCHOLARVPN_VER_MINOR 6
#define SCHOLARVPN_VER_PATCH 0
#define SCHOLARVPN_VER_STRING "1.6.0"
```

`VPN_.rc` 的 `VERSIONINFO`、`ScholarVPN.iss`、CMake 都从这一处取，杜绝“exe 版本 1.5、安装包版本 1.6”这种对不上的情况。

### 3.2 上报内容

| 参数 | 示例 | 说明 |
|---|---|---|
| `ver` | `1.6.0` | 程序版本，必填 |
| `os` | `win-x64` / `linux-x64` | 决定返回哪个平台的包 |
| `cid` | `user2` | 可选，仅用于服务端日志排查；**不做决策依据** |

**不传身份公钥**：更新查询发生在认证之前，此时没有可信身份；传了也无法验证。

## 4. 策略文件与签名

> **实现采用 INI 静态文件**（原因见 7.1）。下面 4.1~4.4 描述的是最初设计的 JSON 接口，
> 保留作对照：**签名覆盖固定顺序的规范串**这个做法两者通用，改文件格式时照搬即可。
> 当前实现的解析代码在 `src/update/update_policy.cpp`。

### 4.1 请求

```
GET /api/client/update?ver=1.6.0&os=win-x64
```

无认证、无 Cookie。放在 `AdminServer` 的公开路由里（与 `/api/info` 同级）。

### 4.2 响应

```json
{
  "action": "optional",
  "latest": "1.7.0",
  "min": "1.6.0",
  "platform": "win-x64",
  "url": "https://dl.example.com/scholarvpn/ScholarVPN-1.7.0-setup.exe",
  "sha256": "9f2c8a41d0b7e3f5...",
  "size": 48213000,
  "notes": "修复认证阶段的边界问题；TCP 分帧性能优化",
  "generated": 1792540800,
  "sig": "base64(Ed25519(上面的规范串))"
}
```

### 4.3 签名的规范串

签名对象**不是整个 JSON**（字段顺序、空白敏感，容易踩坑），而是一个固定顺序的规范串：

```
action\nlatest\nmin\nplatform\nurl\nsha256\nsize\ngenerated
```

客户端按同样顺序拼串验签。新增字段时**只能追加到末尾**，否则老客户端验签失败。

### 4.4 为什么响应也要签名

响应里有 `action=forced`。如果可伪造，攻击者能做到：

1. 劫持明文 HTTP，回 `forced` + 自己的下载地址；
2. 用户被迫安装攻击者的程序（还带管理员权限）。

签名之后，攻击者最多让查询失败（客户端按“查不到→放行”处理），不能改变内容。

> 前提：客户端内置的是**发布公钥**，且 `url` 只在验签通过后才被信任。

## 5. 决策规则

服务端配置（`/etc/default/vpn-server` 或独立 ini）：

```ini
[client_update]
enabled = 1
latest_version = 1.7.0
min_version = 1.6.0          # 低于此版本强制升级
win_x64_url = https://dl.example.com/scholarvpn/ScholarVPN-1.7.0-setup.exe
win_x64_sha256 = 9f2c...
win_x64_size = 48213000
linux_x64_url = https://dl.example.com/scholarvpn/scholarvpn-1.7.0-linux-x64.tar.gz
linux_x64_sha256 = 3b7e...
linux_x64_size = 6124000
notes = 修复认证阶段的边界问题
```

判定：

| 条件 | action | 客户端表现 |
|---|---|---|
| `ver < min` | `forced` | 阻塞弹窗，禁用「连接」，只能「立即更新」或「退出」 |
| `min <= ver < latest` | `optional` | 提示条 + 更新按钮红点，可忽略 |
| `ver >= latest` | `none` | 无提示 |
| 版本串解析失败 | `optional`（保守） | 当作老版本提示，但不阻塞 |
| `enabled = 0` | `none` | 关闭整套机制 |

**版本比较必须按数值**，不能按字符串：`"1.10.0" < "1.9.0"` 是字符串比较的经典事故。

## 6. 客户端行为

### 6.1 GUI 入口

主界面底部（`Switch Server` 与分流按钮之间）加一个文字按钮：

```
[ 全局 ] [ 智能分流 ]
        v1.6.0 · 检查更新        ← 点击立即查询
```

- 平时显示 `v1.6.0`，点击触发查询；
- 有可选更新时变成 `v1.6.0 · 有新版本 v1.7.0`（蓝色）；
- 强制更新时按钮不可点，直接弹阻塞框。

**放在版本号旁边**而不是单独一个醒目按钮：更新不是高频操作，不该抢主流程的视觉焦点。

### 6.2 启动校验

`QtWidgetsClass` 构造完成后（`QTimer::singleShot(0, ...)` 让窗口先画出来），在**后台线程**发起查询：

- 走**直连**（此刻隧道没建，也不该为了查版本建隧道）；
- 超时 5 秒，失败只记日志；
- 结果回到 GUI 线程更新界面。

### 6.3 强制更新的约束

`forced` 时：

1. 模态弹窗，**没有关闭按钮**（`Qt::WindowCloseButtonHint` 不设，Esc 屏蔽）；
2. 「连接」按钮禁用，`ClientApp::start()` 里也加一道闸（防止托盘/命令行绕过）；
3. 只提供两个动作：**立即更新** / **退出程序**；
4. 更新失败（下载失败/校验失败）→ 弹窗保留，提示可重试，**不回到可用状态**。

### 6.4 手动检查

点「检查更新」：

- 查询中显示「检查中…」；
- `none` → 弹「已是最新版本」；
- `optional` → 弹出更新对话框（版本、说明、大小、[稍后] [立即更新]）；
- 查询失败 → 明确告知「无法连接更新服务器」，而不是静默无反应。

## 7. 服务端实现

### 7.1 策略托管：静态文件，不动 webadmin

> ⚠️ **硬约束**：`scholarvpn.homes` 那套后台（`tools/webadmin`，Python）不允许因更新功能而改动。
> 所以**不新增 HTTP 接口**，改为静态文件：

| 文件 | 内容 |
|---|---|
| `update-policy.ini` | 策略（latest / minimum / url / sha256 / notes / generated） |
| `update-policy.ini.sig` | 对上面文件原始字节的 Ed25519 签名（base64） |

放在静态源（nginx），客户端 `GET` 后**先验签再解析**。

这样做的好处：

- 零服务端代码改动、零重启 —— 不会影响任何正在跑的服务；
- 策略可被 CDN 缓存，查询成本为零；
- 运维改文件即改策略（以后可以给 webadmin 加个编辑页，那是独立需求，不阻塞本功能）。

策略文件示例（单平台部署可以省掉平台前缀）：

```ini
# 客户端更新策略
latest    = 1.7.0
minimum   = 1.6.0
notes     = 修复认证阶段的边界问题
url       = https://dl.example.com/scholarvpn/ScholarVPN-1.7.0-setup.exe
sha256    = 9f2c8a41d0b7e3f5a6c9d1e8b4f7a2c5d8e1f4a7b0c3d6e9f2a5b8c1d4e7f0a3
size      = 48213000
generated = 1792540800
```

多平台时用 `win-x64_url` / `linux-x64_url` 这种前缀字段，客户端按 `os` 挑；
两者都没有才算策略无效（客户端按“未配置”处理，正常使用）。

**为什么不放在 `AdminServer` 里**：那是 `vpn_server` 内置的管理面，改它要重新编译并重启
出口端，会打断所有在线连接；而更新策略是低频变更、无状态的内容，静态文件足够。

### 7.2 版本闸门：**不改隧道协议**（有意为之）

> 用户要求：**尽量不碰隧道协议**。因此放弃「在 `auth_req` 里追加版本字段」的方案。

代价必须写清楚：

- 版本判定完全依赖客户端自觉；
- 用户改 hosts 屏蔽 `update-policy.ini`、或用旧版客户端直连，**服务端仍然放行**；
- 也就是说 `forced` 是「防君子不防小人」。

为什么仍然接受：

1. 改协议意味着老客户端**彻底连不上**。一旦 `minimum` 配错，所有用户同时被锁在门外，
   而修复必须重新发包 + 用户手动升级 —— 事故半径太大；
2. 隧道协议是两端最脆弱的耦合点，为「版本提示」这种非核心功能去动它，风险收益不匹配；
3. 真有硬拒绝需求时，有不碰协议的办法（见下）。

**不改协议的加固手段**（按需，非本期）：

- `client_id` 是自由格式字符串（≤255 字节），新客户端可在末尾追加 `|v=1.6.0`；
  服务端识别到后缀就校验，识别不到按「未知版本」放行。
  局限：老客户端永远绕过，只能约束升级后的用户。
- 或者按账号维度下线（把某 `client_id` 从白名单移除），比协议闸门灵活且可回滚。

### 7.3 客户端侧拒绝的表现

阶段 3 失败时返回明确原因码（如 `AUTH_ERR_CLIENT_TOO_OLD`），客户端据此显示「当前版本过低，请更新到 x.y.z」而不是笼统的「认证失败」。错误码表需要同步到客户端。

## 8. 安全

| 威胁 | 缓解 |
|---|---|
| 伪造 `forced` 诱导装恶意包 | 响应 Ed25519 签名；客户端只信验签通过的内容 |
| 篡改安装包 | 安装包 SHA-256 与签名清单比对（复用 `docs/更新系统设计.md`） |
| 中间人替换 `url` | `url` 在签名覆盖范围内，替换即验签失败 |
| 拒绝服务（故意返回 500） | 客户端「查不到→放行」，不影响正常使用 |
| 旧客户端绕过更新 | 服务端认证阶段版本闸门（7.2 A） |
| 降级攻击（装回有漏洞的旧版） | 客户端拒绝安装低于当前版本的包，除非服务端显式 `allow_downgrade` |

## 9. 失败与降级

| 场景 | 行为 |
|---|---|
| 查询超时 / 连不上 | 用**本地缓存**（上次验签通过的策略，含有效期）；无缓存则放行并记日志 |
| **验签失败** | **拒绝使用**（硬要求）：弹窗「更新信息校验失败」，只给「重试 / 退出」。不读缓存、不放行 |
| 配置里 `min > latest`（配错） | 服务端启动时校验并拒绝启动，避免把所有人锁死 |
| 下载中途失败 | 保留已下载部分可续传（或直接重下，包不大） |
| 强制更新时用户断网 | 弹窗保持，提示检查网络，仍不允许使用旧版 |

## 10. 分阶段落地

| 阶段 | 内容 | 验收 |
|---|---|---|
| **P1**（1.5 天） | `version.h` + 静态策略文件（含签名）+ 客户端拉取/验签/决策 + 「检查更新」按钮 | 三种 action 都能正确显示；验签失败被拒 |
| **P2**（1 天） | 强制更新的 UI 约束（阻塞弹窗、禁用连接、`start()` 闸门） | 改配置把 `min` 提到当前版本，客户端被锁死且无法绕过 |
| **P3**（2 天） | 下载 + SHA-256 + 调安装器（复用旧设计） | 从 1.6.0 升到 1.7.0 全流程跑通 |
| **P4**（1 天） | 服务端 AUTH 版本闸门（7.2 方案 A） | 旧版客户端在阶段 3 被拒，错误提示正确 |

P1 + P2 就能满足「服务端决定强制/可选、启动校验」这个核心诉求，P3 才真正能装。

## 11. 验收用例

1. 服务端配 `latest=1.7.0, min=1.6.0`，客户端 1.6.0 → `optional`，显示提示条；
2. 客户端 1.5.9 → `forced`，弹窗不可关闭，「连接」禁用；
3. 客户端 1.7.0 → `none`，无任何提示；
4. 把响应体里的 `forced` 改成 `optional` 但不更新签名 → 客户端**拒绝**并按查询失败处理；
5. 断网启动 → 正常进入，日志有「更新查询失败」，不阻塞；
6. 服务端把 `min_version` 配成 `999.0.0` → 启动时自检拒绝，不会把客户端全锁死；
7. 版本串 `1.10.0` 与 `1.9.0` 比较 → 判定 1.10.0 更新；
8. 强制状态下点托盘「连接」→ 被 `start()` 闸门拦住，状态不变。

## 12. 已确认的决策

| 问题 | 决定 |
|---|---|
| 服务端是否也拒绝旧版本 | **否**：不改隧道协议（7.2）。强制只在客户端生效，接受"改 hosts 可绕过"的局限 |
| 强制时是否允许离线使用 | **不允许**：弹窗只有「立即更新 / 退出」 |
| 策略托管方式 | **静态 INI 文件 + 签名**，不改 webadmin（7.1） |
| 查询通道 | HTTP 明文 + 响应签名；TLS 落地后再换 HTTPS |
| 验签失败的处理 | **拒绝使用**（硬要求）：不降级、不读缓存 |
| 策略文件位置 | 与安装包同源的静态目录，路径写进客户端配置 `UpdatePolicyURL` |

### 12.1 仍待定（实现时再定，不阻塞）

- 策略文件的默认 URL（取决于最终域名与目录结构）；
- 更新包是否需要按渠道（stable/beta）区分；
- 服务端 `min_version` 是否存在「灰度」需求（目前是全局一刀切）。
