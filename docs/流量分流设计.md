# ScholarVPN 流量分流设计

> 状态：**设计稿（未实现）**
> 日期：2026-10-27
> 范围：客户端路由层（Windows / Linux）。**协议、加密、服务端零改动**
> 关联：`docs/更新系统设计.md`（发布流程）、`src/route_manager.cpp`（现有路由能力）

---

## 0. 一页纸

**目标**：国内目标直连（走物理网卡），其余目标走隧道（出口在服务端）。俗称 split tunneling。

**手段**：不动"默认路由指向 TUN"这个前提，而是给**国内 IP 段**追加一批更精确的 bypass 路由。最长前缀匹配天然保证国内段走物理网卡，其余继续走 `0.0.0.0/1` + `128.0.0.0/1` 进隧道。

**为什么不反过来**（默认直连、只给国外 IP 加隧道路由）：国外 IP 段不可枚举，国内 IP 段可枚举。所有主流实现（Clash TUN、sing-box、WireGuard 的 `AllowedIPs` 排除法）都选前者。

| 决策点 | 结论 | 理由 |
|---|---|---|
| 分流依据 | **IP 段（CIDR）优先**，DNS 分流传后续阶段 | 客户端已有路由层，扩展成本最低；不引入 DNS 代理依赖 |
| 策略方向 | 默认走隧道 + 国内段 bypass | 国内段可枚举（~8000 条），国外不可枚举 |
| 数据源 | 内置 `chnroute` + 可选远程更新 | 离线可用；更新走 HTTPS + SHA-256（复用更新系统的校验思路） |
| 路由注入 | Windows `CreateIpForwardEntry2` / Linux `ip -batch` | 复用现有 `RouteManager`，不新造轮子 |
| DNS（P1） | 暂不改，继续走隧道 DNS | 先解决"流量绕路"，再解决"解析污染" |
| DNS（P3） | 本地 DNS 代理 + 域名规则 | 唯一能同时解决污染与 CDN 就近的方案 |
| 默认模式 | `Mode=full`（现状） | 分流是可选能力，不能改变现有用户行为 |

## 1. 现状与缺口

| 现状 | 证据 | 缺口 |
|---|---|---|
| 连接后无条件接管全部流量 | `ClientApp.cpp:521` `add_default_route(m_cfg.Metric)` | 没有"只接管一部分"的开关 |
| 只有服务器 IP 的 bypass | `ClientApp.cpp:421/450` `add_server_bypass_route(m_remote)` | bypass 是单条 `/32`，不支持网段 |
| 路由记录与清理已就绪 | `RouteManager::m_createdRoutes` / `m_addedRoutes` + `clear_routes()` | 可以直接扩展，清理逻辑不用重写 |
| 能查"到某目标的最佳路由" | Windows `GetBestRoute2`（`add_server_bypass_route` 内）；Linux `ip route get` | 已有"找物理网卡与网关"的能力，可直接复用 |
| 无 CIDR 解析 | — | 需要新增 `192.168.1.0/24` → (网络号, 前缀长度) 的解析 |
| 无规则数据 | — | 需要内置国内 IP 列表与加载逻辑 |
| 无 DNS 代理 | DNS 由 `AdapterConfig::set_DNS_IPv4` 直接设成 `8.8.8.8` | 分流后国内域名解析仍绕隧道（P1 已知代价） |

**结论**：路由层扩展约 250 行，DNS 分流是独立的大头（P3，约 500 行）。

## 2. 整体方案

### 2.1 连接时序

```
连接成功（认证通过、拿到虚拟 IP）
  │
  ├─ Mode=full ──→ add_default_route()                       （现状，直接返回）
  │
  └─ Mode=split
       ├─ 1. 加载国内 CIDR 列表（内置 / 远程缓存）
       ├─ 2. 查物理出口：GetBestRoute2(8.8.8.8) / ip route get 8.8.8.8
       │        → (物理网卡, 网关)
       ├─ 3. 批量注入 bypass 路由：<国内 CIDR> via <网关> dev <物理网卡>
       ├─ 4. add_default_route()  ← 仍然要做，否则国外流量不走隧道
       └─ 5. 把"已添加的 CIDR"记进 RouteManager，供断开时整体撤销
```

**关键顺序**：先注入 bypass，再加默认路由。反过来会出现短暂窗口——默认路由已指向 TUN，而国内段还没绕开，少量国内流量被送进隧道（不致命，但会触发一次无谓的 TCP 重连）。

### 2.2 匹配效果

路由表（Linux 视角，Windows 等价）：

```
default via 192.168.1.1 dev eth0            ← 系统原有，保留不动
0.0.0.0/1 dev vpn0 metric 5                  ← 隧道（更精确于 default）
128.0.0.0/1 dev vpn0 metric 5                ← 隧道
1.2.3.4/32 via 192.168.1.1 dev eth0          ← 服务器 bypass（现有）
114.114.114.114/32 via 192.168.1.1 dev eth0  ← 国内段 bypass
223.5.5.0/24 via 192.168.1.1 dev eth0        ← 国内段 bypass
...
```

`0.0.0.0/1` + `128.0.0.0/1` 覆盖全部 IPv4，但前缀长度只有 1；国内段是 `/8`~`/24`，**更长前缀优先**，所以国内目标走物理网卡，其余落回 `/1` 进隧道。

### 2.3 与"服务器 bypass"的关系

服务器 IP 通常是国外地址（不在国内段内），仍需要单独一条 `/32` bypass——否则握手包会被送进还没建立的隧道。这条逻辑**保持不变**。

## 3. 细节方案

### 3.1 数据源与格式

| 文件 | 内容 | 规模 |
|---|---|---|
| `docs/routing/chnroute.txt`（内置） | 每行一个 CIDR，`#` 开头为注释 | 约 8000 行 / 100 KB，聚合后 ~4000 行 |
| 远程清单（可选） | 同上，URL 由 `ChinaIPList` 指定 | 同量级 |

格式刻意选最笨的纯文本：无需 JSON 解析器，加载就是 `getline` + 跳过注释，出错行跳过并计数（不允许一条坏行导致整个分流失效）。

```
# chnroute, generated 2026-10
1.0.1.0/24
1.0.2.0/23
...
```

**聚合**：相邻 CIDR 合并（`1.0.2.0/24` + `1.0.3.0/24` → `1.0.2.0/23`）可减少 40%~50% 条目。聚合算法放在构建期（发布脚本），运行期只读结果——客户端不该在连接时做集合运算。

### 3.2 路由计算

新增 `RouteManager` 接口（两端同名，实现分平台）：

```cpp
// 把 <dest>/<prefix> 指向"通往 probeIp 的物理出口"
// probeIp 用来查物理网关（通常传 8.8.8.8 或服务器 IP）
bool add_bypass_route(const cfgstr& dest, uint8_t prefixLen, const cfgstr& probeIp);

// 批量版本：一次查网关，多次注入（避免每条都查一遍路由）
int add_bypass_routes(const std::vector<std::pair<cfgstr,uint8_t>>& cidrs,
                      const cfgstr& probeIp);
```

**现有 `add_server_bypass_route(ip)` 可以直接用新接口实现**：`add_bypass_route(ip, 32, ip)`。这样"查最佳路由"的代码只有一份。

### 3.3 Windows 实现

复用 `GetBestRoute2` 拿到物理网卡的 `InterfaceLuid` 与 `NextHop`，然后逐条 `CreateIpForwardEntry2`：

```cpp
MIB_IPFORWARD_ROW2 best{};
SOCKADDR_INET probe{};                 // probeIp
GetBestRoute2(nullptr, 0, nullptr, &probe, 0, &best, nullptr);
// best.InterfaceLuid = 物理网卡，best.NextHop = 物理网关

for (auto& c : cidrs) {
    MIB_IPFORWARD_ROW2 row{};
    InitializeIpForwardEntry(&row);
    row.InterfaceLuid = best.InterfaceLuid;
    row.DestinationPrefix.Prefix = c.addr;
    row.DestinationPrefix.PrefixLength = c.prefix;
    row.NextHop = best.NextHop;
    row.Metric = 1;                     // 必须低于隧道路由的 metric
    CreateIpForwardEntry2(&row);        // ERROR_OBJECT_ALREADY_EXISTS 视为成功
    m_createdRoutes.push_back(row);     // 供断开时撤销
}
```

**性能**：`CreateIpForwardEntry2` 实测约 0.2~0.4 ms/条，4000 条约 1~1.6 秒。连接时一次性代价，可接受。超过 8000 条时建议先把列表聚合。

**metric 必须显式设低**：同前缀长度下靠 metric 决胜；设为 1 保证优先于系统原有路由。

### 3.4 Linux 实现

`ip route add` 每条一个进程，4000 条要几十秒——**不可接受**。改用批量：

```bash
# 生成临时批量文件
224.0.0.0/4 via 192.168.1.1 dev eth0
1.0.1.0/24 via 192.168.1.1 dev eth0
...
# 一次进程喂进去
ip -batch /run/scholarvpn-routes.txt
```

`ip -batch` 单进程处理全部条目，实测 4000 条约 0.8~1.5 秒。

**记录删除命令**：与现有 `m_addedRoutes` 一致，存 `ip route del <cidr> via <gw> dev <dev>`，`clear_routes()` 时批量执行（同样用 `-batch`）。

**`ip route add` 重复添加会报 `RTNETLINK answers: File exists`**：批量模式下单条失败是否会中断整个 batch 需实测；保险做法是每条加 `replace` 而不是 `add`（`ip route replace` 幂等）。

> 用独立路由表（`ip rule` + `table 100`）更"干净"，但会让 `ip route get` 的排查结果与用户直觉不一致，且 Windows 端没有对应机制——两端实现差异会变大。**决定：主表直接加，保持两端语义一致。**

### 3.5 DNS 分流（分阶段）

**P1（随分流一起做）**：不碰 DNS。所有查询仍发往隧道内的 `8.8.8.8`。
- 优点：零代码
- 代价：国内域名解析绕一圈（多 100~300 ms），且返回的可能是国外 CDN 节点

**P2（可选）**：DNS 改国内服务器（`223.5.5.5`）。
- 优点：国内域名解析快且就近
- 代价：**国外域名会被污染**（返回错误 IP），而错误 IP 若落在国内段会被直连 → 直接打不开

**P3（正式方案）**：本地 DNS 代理，按域名分流。

```
应用 → 127.0.0.1:53（本客户端）
          ├─ 域名命中「国内域名列表」 → 转发给 223.5.5.5（走物理网卡）
          └─ 未命中                   → 转发给 8.8.8.8（走隧道，无污染）
```

实现要点：
- 监听 `127.0.0.1:53`，需要管理员权限（Windows 上与 `svchost` 抢 53 端口的风险，可改监听 `5353` + 系统 DNS 指向它？不可行，DNS 必须是 53）
- DNS 报文解析只需处理 question 段（域名提取），不需要完整 RR 解析
- 上游选择靠 `sendto` 绑定不同源地址，或直接依赖路由表（国内 DNS 的 IP 在国内段 → 自动直连；8.8.8.8 走隧道）——**这一点很妙：路由分流做好后，DNS 分流几乎免费**
- 域名列表规模：`dnsmasq-china-list` 约 10 万条，内存 8~10 MB，匹配用后缀树或哈希（按 `com.cn` / `qq.com` 这类后缀匹配）

> 注意：P3 的"几乎免费"依赖 3.2 的路由分流已生效。如果用户选了 `Mode=full`，DNS 代理仍然要把国内查询走物理网卡（需要显式 bind），不能只靠路由。

### 3.6 配置项

```ini
[Routing]
Mode=full                     # full=全流量走隧道（默认，现状）| split=国内直连
ChinaIPList=builtin           # builtin | https://example.com/chnroute.txt
BypassSubnets=                # 额外直连网段，逗号分隔，如 192.168.0.0/16,10.0.0.0/8
ProbeIP=                      # 查物理网关用的探测地址，留空=8.8.8.8
```

- `Mode` 默认 `full`，**不改变现有行为**（升级后不会突然分流）；
- `BypassSubnets` 解决"连上后本地打印机/NAS 断了"的问题（当前硬伤）；
- `ProbeIP` 一般不用改；只有在"服务器在本地网段、8.8.8.8 不可达"时才需要指定。

### 3.7 生命周期与异常

| 时机 | 动作 |
|---|---|
| 连接成功 | 加载列表 → 注入 bypass → 加默认路由 |
| 正常断开 | 删默认路由 → 删全部 bypass → 释放列表内存 |
| 断线重连 | **不重复注入**（列表与路由已存在），只重建默认路由 |
| 进程崩溃 | 路由残留 → 下次启动时按"记录的 CIDR"清理（与 DNS 看门狗同一思路） |
| 列表加载失败 | 记 WARN，**降级为 full 模式**（宁可全走隧道，也不要只绕一半导致国内不通） |

**升级/切换模式**：`full → split` 需要注入；`split → full` 需要撤销全部 bypass。切换时先撤后加。

### 3.8 校验与统计

- 启动后打印：`分流已启用：加载 4123 条国内网段，注入耗时 1.2s`；
- 断开后打印：`已撤销 4123 条 bypass 路由`；
- 每条失败的路由计数，超过 10% 失败则整体回滚到 full（避免"半个分流"）。

| 阶段 | 内容 | 验收 |

| **P1**（2 天） | CIDR 解析 + 内置列表 + Windows/Linux 批量注入 + `Mode=split` | 国内 IP 直连、国外 IP 走隧道；断开后路由完全恢复 |

## 6. 验收用例

1. 连接后访问 `114.114.114.114`（国内 DNS）→ 直连，`tracert`/`ip route get` 指向物理网卡；
2. 访问 `8.8.8.8` → 走隧道，源 IP 为服务端出口；
3. 服务器 IP 始终 bypass（握手不断）；
4. 连接后访问本地局域网设备（`192.168.1.50`）→ 正常（依赖 `BypassSubnets`）；
5. 断开后 `/32` 与全部国内段路由消失，系统路由表与连接前一致；
6. `Mode=full` 下行为与改造前**完全一致**（回归）；
7. 列表文件损坏 / 下载 404 → 记 WARN 并降级 full，连接仍成功；
8. 4000 条注入耗时 < 3s（Windows）/ < 2s（Linux）；
9. 断线重连不产生重复路由（路由表条目数不增长）；
10. 崩溃后重启 → 上次残留的 bypass 被清理。

## 7. 风险与限制

| 风险 | 影响 | 缓解 |
|---|---|---|
| 国内 IP 列表过时 | 新 IP 走隧道（慢，但不至于不通） | 发布期更新 + 客户端可配置远程源 |
| CDN 双解析 | 国内域名解析到国外节点，于是走隧道（慢） | P3 DNS 分流解决 |
| 路由条目过多 | 连接慢、低端路由器内存压力 | 聚合；上限 6000 条，超出则按 `/16` 粗化 |
| DNS 污染 | 国外域名解析到被污染的国内 IP → 直连打不开 | P3 才解决；P1 明确告知"仅流量分流" |
| 多网卡 / 双默认路由 | 物理网关选择错误 | 用 `GetBestRoute2` / `ip route get` 探测，而非硬编码 |
| 与系统其他 VPN 共存 | 路由互相覆盖 | 记录并只撤销自己加的条目（现有 `clear_routes` 已保证） |
| Windows 上 `0.0.0.0/1` 与 `/32` 的 metric 冲突 | 国内段仍走隧道 | 显式 `Metric=1`，且用例 1 必须实测 |

## 8. 明确不做

- **不做域名级流量识别**（DPI / SNI 嗅探）：需要解析 TLS ClientHello，跨平台实现成本高，且与"轻量客户端"定位不符；
- **不做进程级分流**（按应用决定走不走隧道）：Windows 需要 WFP 过滤驱动、Linux 需要 cgroup/netns，远超客户端范畴；
- **不做 fake-ip**：与现有"服务端分配虚拟 IP"的语义冲突，且需要完整 DNS 代理栈；
- **不做 IPv6 分流**：当前隧道只承载 IPv4，IPv6 仍按现有策略处理（见 `RouteManager::add_ipv6_default_route` 的注释）。
